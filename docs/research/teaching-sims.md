# Teaching-Oriented Assembly Simulators & Playground Sites — Research

Date: 2026-10-23. Method: web search + GitHub API metadata (license, primary language, last-push date, stars) + npm registry. All "last push" dates are from `api.github.com` on the date above. `[INFERENCE]` marks my judgment, not a measured fact.

Goal context: we need a fully client-side simulator core for a literate-website lesson (register view, single-step, line-synced highlighting), potentially reusable for later lessons on other ISAs, plus embeddable multi-language playgrounds for compiled languages later.

## UX patterns worth borrowing

1. **Step with undo / reverse-step** (venus, CPUlator, vgath-8086). Cheap to implement if the core checkpoints state (or logs an inverse delta) per step; transforms the "oops, stepped too far" experience.
2. **Change highlighting, not just values**: highlight registers/memory cells that changed on the last step (RARS, 8086 playgrounds). Pair with a per-step diff summary ("+1 store to 0x100").
3. **Source ⇄ machine-code side-by-side** with the current instruction highlighted in both (venus). Also gives line-number-anchored assembler errors.
4. **Line-synced error reporting**: every assembler/runtime error carries a source line (and column) so the editor can place squiggles/jump-to-line; runtime faults highlight the offending instruction (lc3web's inline errors are the model).
5. **Tiny fantasy console**: easy6502's memory-mapped pixel screen + RNG port + key port make the first lesson's loops visible in 20 lines of code. A `$screen`-style MMIO region is the single highest-value "steal" for engagement.
6. **Delay slider between steps** (MARIE.js, WebLC3): run-with-visualization at human speed, distinct from instant run.
7. **Disassembly / instruction-by-instruction write log** (CPUlator tracing, vgath write log, emulator-8086-js step log `CS:IP | bytes`): shows *what an instruction did*, which is the pedagogical point.
8. **Runtime pedagogy assertions** (CPUlator): detect classic student bugs — reading uninitialized registers, stack overflow, jumping into data — and emit a friendly explanation instead of garbage execution.
9. **Breakpoints via editor gutter + run-to-breakpoint**, plus step-over (CPUlator, vgath).
10. **URL-parameter program loading** (venus/CS61C share links): lets a literate page deep-link a prepared state without any server.
11. **Embeddable web component + iframe fallback** (Runno `<runno-run>`, LiveCodes SDK): the right *distribution* shape for our executable prose blocks; separate "core library" from "chrome" (6502.ts architecture) so lessons can host their own UI.

## Verdict — vendor vs. write a small interpreter

**Write the RV32I core ourselves (~500–1000 LOC TS); vendor nothing for the first lesson.**

- The surveyed cores split into (a) full-system emulators (v86, rvemu, riscv-rust) — no register/step teaching API, heavy; (b) great teaching apps with **baked-in** cores (venus, RARS, Ripes, VisUAL2, CPUlator, MARIE.js, the 8086 sites); (c) genuinely embeddable libraries — 6502.ts (MIT, wrong ISA), the **Specy family** (@specy/risc-v MIT — right ISA, right shape, very active), and GPL cores (6502js lineage, lc3web) we'd rather avoid in a permissive site.
- The only real vendor candidate is **@specy/risc-v**. It's the right license and API shape, but it inherits all of RARS (pseudo-instructions, float extensions, microservices, MARS assembler dialect) — a large surface we don't control and don't need for RV32I stepping. `[INFERENCE]` Its size/complexity exceeds the 500–1000 LOC custom core, and pedagogical error messages need to be ours anyway.
- A custom core gives exactly what the lesson UX list demands: per-step inverse deltas (undo), source-line mapping for every error, MMIO "screen" port, deliberate pedagogy assertions, and zero dependency risk. RV32I is 37 base instructions + a handful of csrs/ecalls; the two-pass assembler with label resolution is the other half. This is well-trodden territory: lc3/6502 teaching cores of this scope are single-file projects.
- Keep **@specy/risc-v as a differential-testing oracle** (same MIT license): run identical programs through both and diff register/memory traces — free conformance testing without adopting its weight.
- Later compiled-language lessons: **LiveCodes** (MIT, embed SDK, client-side compilers incl. C/C++) is the strongest off-the-shelf embed; **Runno** (MIT, `<runno-run>` web component, WASI) is the lighter-weight alternative. Revisit then; do not couple lesson 1 to them.
