* The single-cycle flaw: one clock for the slowest instruction

The single-cycle machine pays every instruction at the same rate. The clock is a drumbeat; whatever the instruction, it gets one beat to finish. A beat long enough for the slowest marcher is far too long for everyone else, and the marchers that finish early stand still, on the clock, doing nothing.

*The Single-Cycle Datapath* ended on two L6 facts: no functional unit may be used twice in one cycle, and the clock period is decided by the slowest instruction. That slowest instruction is =lw=: its path chains instruction memory, a register read, the ALU, the data memory, and the write-back mux — the whole machine, end to end, in one beat.

Put numbers on the idle time. DrMIPS ships its unicycle datapath with default latencies: instruction memory 300, register file 100, ALU 100, data memory 400, each mux 15. Chain the =lw= path: 300 + 100 + 15 + 100 + 400 + 15 = 930. Chain the =add= path — the same units minus the data memory: 300 + 100 + 15 + 100 + 15 = 530. Every =add= finishes all of its work 400 units before the clock edge, then waits. That is over 40% of each =add='s cycle spent idle. Meanwhile the units an instruction never touches — the data memory during an =add=, the branch adder during a =lw= — idle through every cycle of the program.

Two wastes, one cause: the machine holds one instruction at a time but carries hardware for all of them. The exam angle is already on the table: CPI = 1 says nothing by itself. Performance is IC × CPI × clock period, and this machine buys its CPI of 1 with the longest possible clock. That trade is A15 arithmetic, and this page will run it three ways.

* Multi-cycle: one clock per step [P&H 4.5–4.8; F26 slides post Nov 4 not yet posted]

The waste has a shape: one giant cycle trying to cross the whole datapath in a single go. So cut the path into steps and put the clock edge between them. Each step is short; each instruction takes as many clocks as it has steps.

#+NAME: five-steps
#+BEGIN_SRC text
step 1   IF   fetch        IR = Mem[PC];  PC = PC + 4       every instruction
step 2   ID   decode       read Reg[rs], Reg[rt]; control from opcode
step 3   EX   execute      ALU computes a result, an address, or a compare
step 4   MEM  memory       data memory read (lw) or write (sw); others skip
step 5   WB   write back   write the register file (lw, add, addi); others skip
#+END_SRC

Cutting the cycle changes the machine:

- The fetched word must now survive past its first clock, so it lands in a new instruction register =IR=; anything that must outlive a step gets its own register.
- Fetch and data access happen in different clocks, so one memory can serve both — the single-cycle machine's separate instruction and data memories merge into one.
- The ALU takes turns: address math, branch compares, and arithmetic results all reuse it. The "no unit twice per cycle" rule now applies per step, and a single ALU satisfies it.
- Control stops being a plain lookup and becomes a finite state machine: each state is one step and asserts that step's signals; after decode, the opcode selects which states follow; an instruction whose remaining steps are empty exits the FSM early.

The payoff is a short clock — set by the longest step, not the longest chain — and instructions that pay only for the steps they actually use:

| Instruction class | Steps used | Clocks |
|---+---+---|
| add sub and or slt (R-type) | IF ID EX WB | 4 |
| addi (immediate ALU) | IF ID EX WB | 4 |
| lw | IF ID EX MEM WB | 5 |
| sw | IF ID EX MEM | 4 |
| beq | IF ID EX | 3 |
| j | IF ID EX | 3 |

=beq= leaves after three clocks; =lw= needs all five. Cycles per instruction lands between 3 and 5 for any mix — that is the "CPI 3–5" you will be asked to quote for the multi-cycle machine.

Run the exam-style arithmetic once, with clean numbers. Assume instruction memory 200 ps, register file 100, ALU 100, data memory 200, register write 100. The single-cycle clock is the chained sum, 700 ps. The multi-cycle clock is the longest step, 200 ps. Take a mix of 45% ALU and =addi=, 20% =lw=, 15% =sw=, 20% =beq=:

| Class | Fraction | Clocks | Contribution |
|---+---+---+---|
| R-type and addi | 45% | 4 | 1.80 |
| lw | 20% | 5 | 1.00 |
| sw | 15% | 4 | 0.60 |
| beq | 20% | 3 | 0.60 |
| Weighted CPI | 100% | — | 4.00 |

For 1000 instructions: single-cycle takes 1000 × 1 × 700 ps = 700 ns; multi-cycle takes 1000 × 4.00 × 200 ps = 800 ns. On these numbers the multi-cycle loses by about 14% — its clock is 3.5 times shorter, but its CPI is 4 times bigger. Its guaranteed wins are cost, not speed: one memory instead of two, one ALU for everything, and a clock set by a single step rather than the whole chain. Whether it also wins on time depends on the mix and the latencies, which is why the exam wants the arithmetic, never the slogan.

So the multi-cycle is a stepping stone, and the course treats it as one. The five steps it exposed are about to be run concurrently.

* Pipelining: overlap the steps

P&H's laundry picture, once: wash, dry, fold — one load at a time, and the washer sits idle while you fold. Load 2 into the washer the moment load 1 moves to the dryer, and every stage stays busy; each load still takes exactly as long as before, but from the fill onward one load finishes per wash. Pipelining buys throughput, not latency. The laundry retires here; from now on, instructions.

The formal rule: keep the multi-cycle's five steps and its short clock, change the occupancy. A new instruction enters IF every clock, and every clock edge moves all in-flight instructions one stage forward. The multi-cycle reused its units across the clocks of one instruction; the pipeline reuses them across different instructions in the same clock — while the data memory serves =i1= in =MEM=, the ALU serves =i2= in =EX=, the register file reads =i3= in =ID=, and the instruction memory fetches =i4=.

Overlap re-imposes two demands the multi-cycle had relaxed:

- One memory will not do anymore. Fetch and data access run concurrently every clock, so instruction and data memory split apart again — the very split the multi-cycle merged away.
- The register file must take two reads (ID) and one write (WB) in the same clock: the three-port file from *The Single-Cycle Datapath*, back at full duty.

And one new component appears between every pair of stages: a pipeline register. At each clock edge it captures its stage's outputs — the values and control bits the later stages still need — and only those. The next section runs four real instructions through this machine.

* The staircase: four instructions, eight clocks

Hold this picture: a grid with stages down the side and clocks across the top. Each instruction's five letters march diagonally, each row starting one column later than the row above. That diagonal staircase is the pipeline; the program below is what it runs. Four instructions, one of each class the datapath pages walked — build a constant, load, register add, store — and each depends on an earlier one. The dependency is deliberate; it becomes the next page's whole subject.

#+NAME: staircase
#+BEGIN_SRC mips
# staircase.asm — four dependent instructions, one of each class
        .data
a:      .word 111                  # at 0x10010000: the load's source word
b:      .word 0                    # at 0x10010004: the store's target word
        .text
main:   lui  $s0, 0x1001           # i1: $s0 = 0x10010000, the start of .data
        lw   $t1, 0($s0)           # i2: $t1 = a — needs i1's $s0
        add  $t2, $t1, $t1         # i3: $t2 = 111 + 111 — needs i2's $t1
        sw   $t2, 4($s0)           # i4: b = $t2 — needs i3's $t2 and i1's $s0
        lw   $a0, 4($s0)           # epilogue: read b back
        li   $v0, 1                # print it
        syscall
        li   $v0, 10               # exit
        syscall
#+END_SRC

#+RESULTS:
:222

Run it, then read the panels:

- The =Output= panel prints 222: the load fetched 111, the add doubled it, the store wrote it to =b=, and the epilogue loaded it back.
- The =Program= panel shows nine machine words, one per source line. No pseudo-op doubles this time — each =li= with a small immediate is a single =addiu= row (expansion rules on *Machine Code: R, I, J*). The first four words are the staircase: =lui= at 0x00400000 (encoded 0x3c101001), =lw= at 0x00400004, =add= at 0x00400008, =sw= at 0x0040000C.
- The =Registers= panel ends with $s0 = 0x10010000, $t1 = 0x0000006F (111), $t2 = 0x000000DE (222).
- The =.data= panel's first row reads 6f 00 00 00 de 00 00 00: 111 then 222, little-endian, exactly as *Loads, Stores, and the Byte-Addressed World* taught you to read it.

Now the honesty note this page owes you. This kernel is a serial interpreter: it executes the nine words strictly one at a time. Click the =lw= line's number in the gutter (line 7) to set a breakpoint, Run, then Step — the =hi · lo · pc= panel stops at pc = 0x00400004 and each Step advances one word: 0x00400008, then 0x0040000c, onward (the kernel prints hex lowercase; read 0x0040000c as 0x0040000C). The status line finishes at =finished · exit(0) · 9 steps=. Nine words, nine steps, one whole instruction per step — that is the serial view, and it is the architectural truth: whatever the hardware does underneath, programs are allowed to see this state sequence and nothing else. The staircase below is the overlapped view of the same nine words — the microarchitecture. No panel in this kernel draws pipeline timing; the table is built by hand from the five-stage rule, and the run you just did is its raw material.

| Instruction | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---+---+---+---+---+---+---+---+---|
| i1  lui $s0, 0x1001 | IF | ID | EX | MEM | WB |  |  |  |
| i2  lw $t1, 0($s0) |  | IF | ID | EX | MEM | WB |  |  |
| i3  add $t2, $t1, $t1 |  |  | IF | ID | EX | MEM | WB |  |
| i4  sw $t2, 4($s0) |  |  |  | IF | ID | EX | MEM | — |

Walk the diagonal, clock by clock:

- Clock 1: =i1= in IF. Instruction memory reads 0x00400000, the word =lui $s0, 0x1001=.
- Clock 2: =i1= in ID, control reading opcode 0x0F; =i2= in IF.
- Clock 3: =i1= in EX forms 0x1001 shifted left 16: 0x10010000. =i2= is in ID, reading $s0 — which =i1= has not written yet. Note the debt; the table draws the ideal schedule, in which the value somehow arrives on time. Collecting that debt is the next page's job.
- Clock 4: =i1= in MEM does nothing — a =lui= touches no data memory; MEM is a waiting room for it. =i2= in EX adds 0 to $s0 to form the address 0x10010000 (as drawn, using the not-yet-written value — the debt again). =i3= in ID, reading $t1 — which =i2= has not written yet: the second debt, same shape as the first. =i4= enters IF, and four instructions are in flight.
- Clock 5: the peak. =i1= in WB writes $s0; =i2= in MEM reads 111 from 0x10010000; =i3= in EX computes 111 + 111; =i4= in ID reads $s0 and $t2; and IF fetches the epilogue's =lw=. Five stages hold five different instructions, and every major unit works at once — each unit is used by exactly one stage per clock. Look at $s0: =i4= reads it in the very clock =i1= writes it. That is not the one-use rule at work but the register bank's three ports: two read ports for ID and one write port for WB, split across the cycle so the write lands in the first half and reads sample the fresh value in the second. The course's DrMIPS register bank does exactly that, and it is one of the next page's structural fixes.
- Clock 6: =i2= in WB writes $t1 = 111, one clock after =i3='s EX consumed $t1 — the second debt. =i3='s MEM is another empty waiting room. =i4= in EX computes 0x10010000 + 4.
- Clock 7: =i3= in WB writes $t2 = 222; =i4= in MEM writes 222 to 0x10010004 — the store your =.data= panel showed you.
- Clock 8: =i4='s WB slot is empty. The =RegWrite= signal is 0 for =sw= — the row from *The Control Unit*'s table — so there is nothing to write back. The pipeline drains.

Count the alternatives for these same four instructions. Single-cycle: 4 long clocks. Multi-cycle: 4 + 5 + 4 + 4 = 17 short clocks. Pipeline: 8 short clocks — and the 8 is not a per-instruction cost, it is 4 instructions plus a 4-clock fill. A straight-line stream of N instructions needs N + 4 slots; the fill is paid once. In DrMIPS terms, the =Assembled= table paints the five stages (IF blue, ID green, EX yellow, MEM red, WB magenta), and the =Datapath= view lights the active components as you step; the staircase is that picture unrolled over time.

* What travels in the pipeline registers

A stage hands the next stage a bundle: not the whole instruction, just what the remaining stations still need. After ID the instruction word itself leaves the datapath; what rides forward are its read values, its fields, and the control bits ID computed. Each bundle is a pipeline register, and the course's DrMIPS pipeline datapath names all four and lists their exact contents:

| Register | Between | Carries forward |
|---+---+---|
| IF/ID | IF and ID | NewPC (32), Instruction (32) |
| ID/EX | ID and EX | ReadData1, ReadData2, NewPC, Imm (32 each); Rs, Rt, Rd (5 each); RegDst, ALUSrc, Branch, MemRead, MemWrite, MemToReg, RegWrite (1 each); ALUOp (2) |
| EX/MEM | EX and MEM | Result, ReadData2, Target (32 each); Zero (1); RegBankDst (5); Branch, MemRead, MemWrite, MemToReg, RegWrite (1 each) |
| MEM/WB | MEM and WB | Result, ReadData (32 each); RegBankDst (5); MemToReg, RegWrite (1 each) |

Some passengers look strange until you ask who needs them:

- =NewPC= (the PC + 4 that IF computed) rides as far as =ID/EX= because EX needs it to form a branch target: Target = NewPC + (imm shifted left 2) — the same arithmetic drilled on *Machine Code: R, I, J*.
- =Rs=, =Rt=, =Rd= ride along as register numbers even though the values were already read in ID. The hazard and forwarding units of the next page compare register numbers between stages; without the numbers riding, there is nothing to compare.
- =ReadData2= travels all the way into =EX/MEM= — for a store it is the data to be written, and it is needed at MEM, not at EX.
- The control signals from *The Control Unit* are latched into =ID/EX= and each is consumed by exactly one stage: =ALUSrc= is used by EX, =MemWrite= by MEM, =RegWrite= by WB. That is why the bundles shrink stage by stage: =MEM/WB= is down to five fields, every used-up signal and value dropped along the way.
- =RegBankDst= is DrMIPS's name for the write-register number after the =RegDst= mux — the rt-or-rd decision is made in EX, where the mux takes its inputs from the ID/EX outputs, and its result latches into =EX/MEM.RegBankDst= and must survive to WB, two stages later.
- =Zero= and =Target= sit in =EX/MEM= because the course's pipeline applies a taken branch's new PC from the MEM boundary, so the comparison result and the target address must both cross out of EX. (The course's pipeline datapaths drop =j= entirely to keep the PC mux branch-only; jump returns as a control exercise.)

A pipeline register is a contract: exactly what the next stage needs, and nothing it does not. ILO6 on the final covers the pipelined processor, and these bundles are its vocabulary — know what each field is for, not merely that it exists.

* Ideal CPI = 1, and what limits the speedup

The fill is a fixed cost, like a ramp onto a highway: you pay it once, then travel at full rate. Formalize it. A straight-line stream of N instructions on a 5-stage pipeline occupies N + 4 clock slots, so CPI = (N + 4) / N = 1 + 4/N. At N = 1000, CPI = 1.004. At N = 4 — the staircase above — CPI = 8 / 4 = 2.0. Pipelines are throughput machines; short programs pay the fill without collecting the dividend.

The clock is the other half. A pipeline runs at the speed of its slowest stage, plus the delay of the pipeline registers themselves: T_pipe = max(stage delays) + register overhead. Now the A15-style worked chain, reusing the clean numbers from the multi-cycle section (stages 200, 100, 100, 200, 100 ps; single-cycle clock 700 ps; register overhead 10 ps):

- Single-cycle: 1000 × 1 × 700 ps = 700,000 ps = 700 ns.
- Pipeline, clock 200 + 10 = 210 ps: (1000 + 4) × 210 ps = 210,840 ps, about 211 ns. Speedup 700,000 / 210,840, about 3.3.
- Balance the stages — 140 ps each, still 10 ps of register overhead, clock 150 ps: 1004 × 150 ps = 150,600 ps. Speedup about 4.6.
- Make the registers free too: at N = 1000 the speedup is 700,000 / 140,560 = 4.98, and as N → ∞ it approaches the ceiling 700 / 140 = 5.0. The ceiling is the stage count, reached only with perfectly balanced stages, zero register cost, and an infinitely long program.

| Machine | Clock | CPI | Time, 1000 instructions |
|---+---+---+---|
| single-cycle (the machine of The Single-Cycle Datapath) | 700 ps | 1.000 | 700 ns |
| multi-cycle | 200 ps | 4.000 | 800 ns |
| 5-stage pipeline, ideal | 210 ps | 1.004 | 211 ns |

Two brakes keep real pipelines under the ceiling. Imbalance: the slowest stage sets the clock for everyone, so an unbalanced pipeline idles inside every cycle — the single-cycle flaw again, one level up. Register overhead: every pipeline register adds its delay to every instruction, every clock, and it is also why cutting the machine into 50 stages buys little — each cut adds another register, and finer cuts are harder to balance. Memory is the usual long pole: the two memory stages dominate any realistic split, and making memory effectively fast is the subject of *The Memory Hierarchy*, two pages ahead.

The exam pattern: a table like this with different numbers, and a demand for units. Compute each machine's IC × CPI × clock period separately, convert ps to ns once, and only then take the ratio — "faster" is a time ratio, stated in the right direction.

* What breaks: three hazards

The staircase quietly made two promises: that values arrive on time, and that the instruction after a branch is the right one. Overlap breaks both, in three named kinds. The next page, *Hazards, Forwarding, Stalls*, is devoted to the repairs; the labs load four DrMIPS pipeline variants that show each break unfixed.

- Structural: two instructions want the same unit in one clock. The staircase brushed one at clock 5 — =i1='s WB write and =i4='s ID read hitting the register file together — repaired by the three-port file with same-cycle write-to-read. IF and MEM want memory every clock, repaired by the instruction/data memory split.
- Data, the RAW kind (read after write): =i2='s EX needs $s0 one clock before =i1='s WB produces it; =i3= needs $t1 the same way. The producer is still inside the pipe when the consumer wants the value. The repair is forwarding — routing the value from the pipeline register it already sits in straight back to EX — with loads as the hard case, since the value does not exist until MEM and costs a one-clock stall.
- Control: a taken =beq= decides the next PC late — in the course's pipeline the new PC is applied from the MEM boundary — while three younger instructions are already fetched and partly executed. If the branch was taken, they are wrong-path work and must be flushed. Resolve earlier, predict, or pay the flush: the arithmetic belongs to the next page.

The punchline to carry forward: ideal CPI = 1 is the start of the story, not the end. Effective CPI = 1 + stalls + flushes, and every hazard above is a term in that sum.
