#+TITLE: ELEC2350 · 6 · Procedures and the Stack
#+SUBTITLE: jal remembers where you came from; the stack remembers everything else

So far this series has run one instruction stream at a time. /The Machine
Model/ gave you the fetch loop and the 32 registers, /Arithmetic and Logic/
and /Loads, Stores, and the Byte Addressed World/ filled them and touched
memory, /Branches, Loops, and C Translation/ bent the program counter with
labels, and /Machine Code: R, I, J/ showed =jal= and =jr= as 32-bit words.
This page puts the pieces together the way real programs do: procedures that
call each other, pass arguments, return results, and stay out of each other's
registers. One register, =$ra=, and one memory region, the stack, carry the
whole story. Every trap in this story is runnable below, and the kernel
reports each one honestly.

* A call is a detour with a return ticket

A procedure call is a detour. The caller — the code doing the calling —
parks its arguments where the callee can find them, jumps away, and expects
to continue exactly where it left off when the callee is done. MIPS fixes
the meeting points in the register set: the first four arguments travel in
=$a0= through =$a3=, results come back in =$v0= (and =$v1=), and control
moves with just two instructions. The same code is caller and callee at
different moments: =main= calls =max=, so =main= is the caller and =max= is
the callee. Every program so far in this series was a single =main=; from
here on, =main= is just the first caller.

Two instructions do the moving. =jal label= (jump and link) does two things,
in this order: first =$ra = PC+4= — it writes the address of the instruction
just after itself into register 31 — and then it jumps to =label=. =jr $ra=
(jump register) takes the content of =$ra= as an address and jumps there.
The order inside =jal= matters when you trace by hand: write the link first,
then the jump. This kernel has no branch delay slots — the same simplification
SPIM and MARS make in teaching mode — so =PC+4= is literally the next row in
the =Program= panel. Plain =j= cannot replace =jal=: a =j=-based callee would
need a hardcoded label to return to, one per caller. =jal= remembers, so any
number of callers can share one callee.

The first example is the friendliest case: a leaf procedure, one that calls
nothing else.

#+NAME: max-leaf
#+BEGIN_SRC mips
# leaf-max.asm — max(a, b): a leaf procedure needs no stack at all
        .text
main:   li      $a0, 17                 # first argument
        li      $a1, 42                 # second argument
        jal     max                     # call: $ra <- address of the move below
        move    $a0, $v0                # the result arrives in $v0
        li      $v0, 1                  # print it
        syscall
        li      $v0, 10                 # exit
        syscall
max:    slt     $t0, $a0, $a1           # $t0 = 1 if a < b
        beq     $t0, $zero, amax        # a >= b: a is the max
        move    $v0, $a1                # else b is the max
        jr      $ra                     # return to the caller
amax:   move    $v0, $a0
        jr      $ra                     # return to the caller
#+END_SRC

#+RESULTS:
:42

Run it, then look at the =Registers= panel: after the program exits, =$ra=
still reads =0x0040000c=, the address of the =move= one row below the =jal=.
The =Program= panel shows the call encoded as =0x0c100008= — opcode 3, target
field = =0x00400020= shifted right by 2, which is =max='s address (the field
arithmetic is from /Machine Code: R, I, J/) — and every =jr $ra= as
=0x03e00008=, the value printed on the course reference card. Better still:
set a breakpoint on line 5 (click the =jal= row's line number in the gutter),
Run, then Step once. Two things change in that single step: =$ra= lights up
=changed= with =0x0040000c=, and the current-row marker jumps to =max=. That
one step was the entire call.

Why could =max= ignore memory? It is a leaf: it borrows =$t0=, leaves its
answer in =$v0=, and =$ra= is still holding the caller's address when
=jr $ra= runs. Nothing it does can destroy the return ticket. The first
procedure that calls another procedure loses this luxury, and that is where
the stack enters.

The exam version of this section is one line: /what happens when =jal hello=
is fetched?/ Answer: =$ra = PC+4=, then the jump to =hello= — both, in that
order.

* The stack: a scratchpad that grows down

One =jal= writes one return address into one register. The moment a
procedure needs to call another procedure, the second =jal= overwrites the
first return address, so something has to hold it. That something is a
region of memory at the top of the address space called the stack. Its
whole personality comes from one design decision: it grows DOWN, toward
lower addresses. Think of the stack as a pile of full words with empty
space below it: pushing a word moves the pile's bottom edge down, popping
moves it back up.

Register 29, =$sp=, is the stack pointer, and it always points at the last
full word on the stack — never at the empty space below (L3 p.71: the stack
pointer "points to the last word pushed into the stack"). In this kernel
=$sp= starts at =0x7fffeffc=, near the top of memory, already pointing at
a usable word.

A push is two instructions, and their order is the lesson: move =$sp= down
first, then store at =0($sp)=. A pop reverses it: load from =0($sp)= first,
then move =$sp= back up. Store before the decrement and you overwrite the
last full word; load after the increment and you read the word you just
gave back.

#+NAME: pushpop
#+BEGIN_SRC text
# push one register (T6 p.16 / L3 p.71 pattern)
addi  $sp, $sp, -4        # make room FIRST: $sp moves down one word
sw    $s0, 0($sp)         # then store into the new top of the stack

# pop it back
lw    $s0, 0($sp)         # read the top FIRST, while $sp still points at it
addi  $sp, $sp, 4         # then give the word back
#+END_SRC

One honesty note about the panels: the =.data= hexdump shows the first 256
bytes of =.data= at =0x10010000=. The stack lives at the opposite end of
memory and is not displayed anywhere as bytes — you watch it through =$sp=
in the =Registers= panel. The rhythm to recognize: a =addi $sp, $sp, -8=
followed by two =sw=s pushes two words, and =$sp= reads eight lower than
before, =0x7fffeffc= becoming =0x7fffeff4=. You will see exactly that
rhythm in every runnable block below this point.

The exam angle: direction and pointer discipline. Pushing decreases =$sp=;
popping increases it; =$sp= always points at the last full word. A question
that hands you three pushes and asks for =$sp= wants subtraction, not
addition, and wants it in multiples of 4.

* Who saves what: the register contract

Registers are shared furniture. The caller is sitting on some of them when
it calls; the callee wants some of them for its own work. Neither can see
inside the other: the callee does not know which registers this caller —
or any of its other possible callers — is using, and the caller does not
know which registers the callee will use, since the callee may itself call
further procedures (T6 p.7 states both halves of this). The MIPS convention
resolves the standoff by assigning every register an owner who is
responsible for keeping its value safe across a call:

| Register    | Number | Use                                   | Preserved across a call? |
|-------------+--------+---------------------------------------+--------------------------|
| $zero     |      0 | constant 0                            | n.a.                     |
| $at       |      1 | assembler temporary                   | no                       |
| $v0–$v1 |    2–3 | function results, expression eval     | no                       |
| $a0–$a3 |    4–7 | arguments                             | no                       |
| $t0–$t7 |   8–15 | temporaries                           | no                       |
| $s0–$s7 |  16–23 | saved temporaries                     | yes                      |
| $t8–$t9 |  24–25 | temporaries                           | no                       |
| $k0–$k1 |  26–27 | reserved for the OS kernel            | no                       |
| $gp       |     28 | global pointer                        | yes                      |
| $sp       |     29 | stack pointer                         | yes                      |
| $fp       |     30 | frame pointer                         | yes                      |
| $ra       |     31 | return address                        | no                       |

The table reads as a duty list. The =no= registers — =$t=, =$a=, =$v=,
=$ra=, =$at= — are caller-saved: any callee is free to wipe them, so a
caller with a live value there must push it before =jal= and pop it after.
The =yes= registers — =$s0= through =$s7= — are callee-saved: a callee that
uses one must save it on entry and restore it before =jr $ra=. =$sp= is
preserved in a stricter sense: the callee may move it — every push does —
but it must be back where it started when the callee returns. =$gp= and
=$fp= are preserved the same way. =$zero= needs no protection because
writes to it are discarded.

T6's second worked example shows both sides of the contract in one snippet:

#+NAME: t6-caller-save
#+BEGIN_SRC text
# T6 (tutorial 7), p.14 — caller on the left, callee on the right, verbatim
# caller                                # callee (update_func)
    addi $a0, $t0, 2                update_func:
    add  $a1, $s0, $zero                addi $sp, $sp, -4
    add  $a2, $s1, $t0                  sw   $s0, 0($sp)
    addi $a3, $t0, 3                    add  $t0, $a0, $a1
    addi $sp, $sp, -4                   add  $t1, $a2, $a3
    sw   $t0, 0($sp)                    sub  $s0, $t0, $t1
    jal  update_func                    lw   $s0, 0($sp)
    add  $v0, $s0, $zero                addi $sp, $sp, 4
    lw   $t0, 0($sp)                    jr   $ra
    addi $sp, $sp, 4
    add  $t2, $v0, $zero
#+END_SRC

Read the two columns together. The caller saves =$t0= because it holds a
live value needed across the call, and does not save =$t2= because =$t2= is
written fresh from =$v0= after the call: nothing live, nothing to save.
The callee saves =$s0= because it computes into =$s0=. That one contrast
is the entire exam question "why don't we need to save =$t2=?" (T6 p.14).
One caution if you trace the arithmetic: the slide is loose with results —
=update_func= computes its answer into =$s0= and then restores the caller's
=$s0= over it, so the value never actually reaches the caller. The slide
teaches the save/restore choreography, not result passing.

One register you should never borrow: =$at=. T6's first example (p.13)
uses it as scratch — do not copy that habit. =$at= belongs to the
assembler: =la=, large =li= values, and immediate branches all expand
through it, as the two-row listings in these pages keep showing.

* The nested-call trap: one register, two return addresses

=$ra= is a single register, and every =jal= writes it. A leaf procedure is
safe because nothing runs between its =jal= and =jr $ra= that could touch
the link. A non-leaf procedure — one that calls another procedure — is not
safe, because its own =jal= replaces its caller's return address with its
own. T6 p.15 walks the trap with concrete addresses. At =0x0400000c= sits
=jal hello=: it sets =$ra = 0x04000010=, the instruction after itself, and
jumps to =hello= at =0x04000044=. Deeper in =hello=, at =0x0400004c=, sits
=jal back=: it sets =$ra = 0x04000050= and jumps to =back= at
=0x04000064=. Now =back= finishes and runs =jr $ra= — it lands on
=0x04000050=, which is correct, because that =jal= wrote =$ra= for =back=.
Then =hello= reaches its own =jr $ra= at =0x04000054= — but =$ra= still
says =0x04000050=. The jump lands one instruction above itself, inside
=hello=, and the way back to =main= at =0x04000010= is gone. That slide is
T6's "something wrong" moment.

Here is the same shape, runnable, at this kernel's text base =0x00400000=.
=outer= should call =inner=, add =n= to the result, and return to =main=.
It forgets that its own =jal= destroys its ticket home.

#+NAME: nested-broken
#+BEGIN_SRC mips
# broken-nested.asm — outer calls inner without saving $ra: runaway
        .data
pre:    .asciiz "main: calling outer\n"
        .text
main:   li      $v0, 4                  # print the banner first
        la      $a0, pre
        syscall
        li      $a0, 5                  # the argument
        jal     outer                   # $ra <- address back in main
        move    $a0, $v0                # ...never reached
        li      $v0, 1
        syscall
        li      $v0, 10
        syscall
outer:  jal     inner                   # fault-demo: $ra now points inside outer
        add     $v0, $v0, $a0           # outer(n) = inner(n) + n
        jr      $ra                     # jumps to the line above, forever
inner:  sll     $v0, $a0, 1             # inner(n) = 2n
        jr      $ra                     # works: jal inner set $ra for me
#+END_SRC

#+RESULTS:
:main: calling outer

Run it and read what this kernel actually does, because it is not a clean
error. The console prints the banner and nothing else. The block's status
line goes red with: instruction budget of 1,000,000 steps exceeded — this
looks like an infinite loop. The program never prints its answer and never
exits; the runaway burned the entire run budget.

Now investigate. Set a breakpoint on line 17 (the =jr $ra= inside
=outer=), Run, and look at the =Registers= panel: =$ra = 0x00400030=, and
=$sp= still reads =0x7fffeffc= — nothing was ever pushed. Scan the address
column of the =Program= panel: =0x00400030= is the =add= row, one row above
the breakpoint. Main's =move= sits at =0x00400018=, and that address no
longer exists in any register. Step a few times and watch the current row
ping-pong between the =add= and the =jr= while =$v0= climbs 15, 20, 25, 30:
the machine is obeying =$ra= to the letter, and =$ra= points at the wrong
place.

Notice what did not happen: no fault at the =jr= itself. =0x00400030= is a
valid =.text= address, so the jump is legal and the machine takes it. This
kernel only rejects a =jr= to an address outside =.text= — for example
=jr $ra= in =main= before any =jal=, when =$ra= still holds its initial 0,
which stops with a message about jumping to =0x00000000= and advises
exiting with syscall 10 instead. A wrong-but-legal return address produces
no error at all, just wrong behavior — which is worse, and is exactly why
T6 drills this by hand.

The fix is to spill =$ra= on the stack around the call that would clobber
it — T6 p.16's pattern: push =$ra= before the inner =jal=, pop it after.
Here is the same program, repaired:

#+NAME: nested-fixed
#+BEGIN_SRC mips
# fixed-nested.asm — outer spills $ra around the call to inner
        .data
pre:    .asciiz "main: calling outer\n"
res:    .asciiz "main: outer(5) = "
        .text
main:   li      $v0, 4                  # print the banner
        la      $a0, pre
        syscall
        li      $a0, 5                  # the argument
        jal     outer                   # $ra <- back to main
        move    $s0, $v0                # park the answer ($s0 is callee-saved)
        la      $a0, res
        li      $v0, 4                  # print the label
        syscall
        move    $a0, $s0
        li      $v0, 1                  # print the number
        syscall
        li      $v0, 10                 # exit
        syscall
outer:  addi    $sp, $sp, -8            # push: a two-word frame
        sw      $ra, 4($sp)             # spill MY return address
        sw      $a0, 0($sp)             # save MY argument
        jal     inner                   # safe now: $ra is parked
        lw      $a0, 0($sp)             # restore my argument
        add     $v0, $v0, $a0           # outer(n) = inner(n) + n
        lw      $ra, 4($sp)             # recover the REAL return address
        addi    $sp, $sp, 8             # pop the frame
        jr      $ra                     # back to main, correctly
inner:  sll     $v0, $a0, 1             # inner(n) = 2n
        jr      $ra                     # leaf: nothing to save
#+END_SRC

#+RESULTS:
:main: calling outer
:main: outer(5) = 15

Run it: =main: outer(5) = 15= prints, and the program exits cleanly. Then
verify the mechanism in the panels, because the fix is where the state
gets interesting. Set a breakpoint on line 23 (the =jal inner=) and Run:
=$ra= reads =0x00400018=, main's address, and =$sp= reads =0x7fffeff4= —
the link is intact AND already parked at =4($sp)=. Step once: =$ra=
flips to =0x00400050=, the row just after =jal inner= — the clobber has
happened, and it is harmless now. Reset, put the breakpoint on line 26
(the =lw $ra=) and Run: =$ra= still reads the stale =0x00400050=. Step
once: =$ra= flips back to =0x00400018=, loaded from the stack. The real
ticket was in memory the whole time.

Two smaller notes on this block. =inner= happens not to touch =$a0=, but
the convention says any callee may, so =outer= keeps its argument in the
frame too — a caller that needs an argument after a call must keep it
somewhere safe: the stack or a =$s= register. And =main= parks the answer
in =$s0= before printing, for the same reason: the print syscalls are not
calls, but the habit of moving precious values into callee-saved registers
across activity is the contract in action.

* The callee's duty: keeping the $s registers intact

Flip the contract around. The caller parks its precious values in =$s=
registers precisely because it does not have to save them — the callee
does that, if it uses them. T6 p.11 asks the question directly: the
callee uses =$s4= and =$s5=, so do we need to save those registers in the
caller part of the program? No. The callee saves them, because they are
callee-saved. Here is T6's =update= pattern made runnable — the caller
proves the point by printing =$s4= after the call:

#+NAME: callee-save
#+BEGIN_SRC mips
# callee-save.asm — the callee owns saving $s4/$s5 (T6 pattern)
        .text
main:   li      $s4, 111                # caller's values live in $s registers
        li      $s5, 222
        li      $a0, 3                  # two arguments
        li      $a1, 4
        jal     update                  # update(3, 4)
        move    $a0, $v0                # print the result
        li      $v0, 1
        syscall
        li      $a0, 32                 # then a space
        li      $v0, 11
        syscall
        move    $a0, $s4                # print $s4: still 111
        li      $v0, 1
        syscall
        li      $v0, 10                 # exit
        syscall
update: addi    $sp, $sp, -8            # push a frame for two saved registers
        sw      $s4, 4($sp)             # save
        sw      $s5, 0($sp)
        add     $s4, $a0, $a1           # body: free to use $s4/$s5
        sll     $s5, $a1, 2             # $s5 = b * 4
        add     $v0, $s4, $s5           # the result goes out in $v0
        lw      $s5, 0($sp)             # restore
        lw      $s4, 4($sp)
        addi    $sp, $sp, 8             # pop the frame
        jr      $ra
#+END_SRC

#+RESULTS:
:23 111

The output is the contract made visible: =update(3, 4)= returns
=(3+4) + 4*4 = 23= in =$v0=, and the caller's =$s4= survived the call with
its 111 intact. Watch the save and restore happen. Set a breakpoint on
line 24 (the =add $v0=) and Run: the =Registers= panel reads =$s4 = 7= and
=$s5 = 16= — =update= really did wipe both, exactly as it is allowed to.
Now Step through the two =lw= rows: =$s5= flips back to 222, then =$s4=
back to 111, and after the =addi $sp, $sp, 8= the stack pointer is back at
=0x7fffeffc=. The frame existed for exactly the duration of the call.

Two honesty notes. T6's original slide (p.13) computes its result into
=$at= and never returns a value; this version returns in =$v0=, which is
what the convention demands, and avoids =$at= for the reason above. And
the frame is push-all-then-pop-all, with =$sp= moved once by 8 — T6's
exact shape — rather than two separate 4-byte pushes; both are correct,
and one =addi= per boundary is the tidier habit.

Try the failure: delete the two =$s4= lines (the =sw= on line 20 and the
=lw= on line 26) and Run again. The second number prints 7 — =$s4=
holding =update='s leftover =3+4= — while the first still prints 23. One
missing save, one silently wrong register, no error anywhere. That is the
callee's duty in one experiment.

* Recursion: factorial, six frames deep

Recursion is not a new mechanism. A recursive procedure is just a non-leaf
whose inner call happens to target itself, so the nested-call trap and its
stack fix apply on every level. Each active call needs its own =$ra= and
its own copy of =n=; the stack hands each one a private 8-byte frame, and
every path through the procedure must give the frame back. Here is
=factorial(5)= with full discipline:

#+NAME: fact-rec
#+BEGIN_SRC mips
# fact-rec.asm — recursive factorial(5), full stack discipline
        .text
main:   li      $a0, 5                  # n = 5
        jal     fact                    # fact(5)
        move    $a0, $v0                # print the answer
        li      $v0, 1
        syscall
        li      $v0, 10                 # exit
        syscall
fact:   addi    $sp, $sp, -8            # push: room for $ra and n
        sw      $ra, 4($sp)             # spill the return address
        sw      $a0, 0($sp)             # save this call's n
        li      $v0, 1                  # the base-case result
        beq     $a0, $zero, done        # n == 0: stop recursing
        addi    $a0, $a0, -1            # n - 1
        jal     fact                    # recurse: clobbers $ra and $a0
        lw      $a0, 0($sp)             # restore this call's n
        mult    $a0, $v0                # hi:lo = n * fact(n-1)
        mflo    $v0                     # result <- low 32 bits
        lw      $ra, 4($sp)             # restore the return address
        addi    $sp, $sp, 8             # pop the frame
        jr      $ra
done:   lw      $ra, 4($sp)             # base case returns 1
        addi    $sp, $sp, 8
        jr      $ra
#+END_SRC

#+RESULTS:
:120

This block is the page's centerpiece for panel work, because the whole
recursion is visible in =$sp=. Set a breakpoint on line 10 (the =fact=
entry) and Run. The first pause stops before =fact='s first instruction,
so =$sp= still reads its start value =0x7fffeffc=, and =$ra = 0x00400008=
points back into =main=. Press Run again — it continues to the next visit
of line 10: =$sp = 0x7fffeff4=. Again: =0x7fffefec=. Keep going through
=0x7fffefe4=, =0x7fffefdc=, and =0x7fffefd4= at the sixth pause — that one
has =$a0 = 0=, the base case, and on every pause after the first, =$ra=
reads =0x00400038=: the recursive calls return into =fact= itself, just
after the inner =jal=. Six pauses, and =$sp= dropped exactly 8 bytes per
call. Step once from the sixth pause and =$sp= reaches =0x7fffefcc= —
48 bytes below the start, six frames of 8 bytes, the deepest point of the
recursion.

Now Run once more, with the breakpoint still set: no line-10 visit remains
on the way up, so the program runs to completion. The base case returns 1;
each frame on the way up restores its own =n=, multiplies it in
(=5 × 4 × 3 × 2 × 1=), restores its own =$ra=, and pops; the =Output=
panel shows 120, and the =Registers= panel ends with =$sp= back at
=0x7fffeffc= and =$ra= back at =0x00400008=. Every frame paid back exactly
what it borrowed — that symmetry is what "the callee restores =$sp="
means.

Two details worth flagging. =mult= and =mflo= are the reference sheet's
multiply pair: =mult= writes the full 64-bit product to =hi:lo=, =mflo=
brings the low 32 bits into =$v0= (the 3-operand =mul= is a pseudo-op that
expands to exactly these two rows — write the real pair in an exam
answer). And notice that BOTH exits from =fact= — the recursive path and
the =done= base case — restore =$ra= and pop the frame. What happens if
=done= forgets the pop? Delete its =addi $sp, $sp, 8= and Run: the
program still exits cleanly, and =$sp= still ends at =0x7fffeffc=,
exactly where it started — the deepest frame's epilogue ends up running
twice, which accidentally pays back the base frame's missing pop — but
the output is =0=, not =120=. Every unwinding frame restored the
frame-below's saved =n= — the base case's 0 — instead of its own, and
one zero multiplies the whole chain away. Missing cleanup does not always
announce itself with a crash or a crooked stack pointer; it corrupts
results while the bookkeeping lucks back into place. Discipline means
every exit path restores, because you cannot count on the luck.

* $fp frames: the deeper machinery

Everything above is =$sp=-relative addressing, which is all T6 uses — none
of its examples mention a frame pointer. Lecture 3 (pp.72–76) goes one
level deeper and names the region between =$fp= and =$sp= the procedure
frame: =$fp= points at the first word of the frame, =$sp= at the last, the
address in =$fp= is always higher than in =$sp=, and the callee sets up
both. The reason a fixed =$fp= exists: =$sp= keeps moving during a
procedure — every push for a nested call moves it — so locals addressed
from =$sp= would need recomputing after every push. =$fp= is planted once
at entry and holds still for the whole body.

#+NAME: fp-frame
#+BEGIN_SRC text
# L3 pp.75-76 frame entry/exit, concrete 16-byte frame — read-only
# entry (callee):
addi  $sp, $sp, -16       # 1. allocate: subtract the frame size
sw    $s0, 12($sp)        # 2. save callee-saved registers...
sw    $ra, 8($sp)         #    ...$ra among them...
sw    $fp, 4($sp)         #    ...and the caller's $fp
addi  $fp, $sp, 12        # 3. $fp = $sp + frame_size - 4: first word
# ...body: $fp-relative addresses stay valid even while $sp moves...
# exit (callee):
lw    $fp, 4($sp)         # restore in reverse order
lw    $ra, 8($sp)
lw    $s0, 12($sp)
addi  $sp, $sp, 16        # delete the frame
jr    $ra                 # return
#+END_SRC

That is the full machinery: allocate, save the callee-saved set including
the old =$fp=, plant the new =$fp=, work, then restore, delete, and
return. For this course, keep the priorities straight: T6 and its drills
are =$sp=-only, so the push/pop motion and the who-saves-what table are
the graded skills. Recognize =$fp= when a diagram shows it, know it is a
fixed base while =$sp= moves, and do not spend exam time laying out frames
by hand unless a question asks for L3-depth detail.

* Exam drills this page prepares you for

- A12, stack and procedure-call questions — the core of this page. The
  who-saves-what table (T6 p.9's "Preserved across a call?" column); the
  push/pop order ($sp= moves first on push, last on pop); "do we need to
  save those registers in the caller part?" (no for =$s= registers — the
  callee's job); "why don't we need to save =$t2=?" (nothing live across
  the call); and the nested-call trace "what happens when =jal hello= is
  fetched?" ($ra = PC+4=, then the jump) with the second-=jal= clobber and
  its push/pop fix.
- A1 extensions — C functions with calls now translate with the full
  calling sequence: arguments into =$a0=–=$a3=, =jal= at the call, the body
  in =$t=/$s= registers by the house rules from /Branches, Loops, and C
  Translation/, the result in =$v0=, =jr $ra= at the end, and the stack
  used exactly where a live value crosses a call.
- A6-style traces — predicting register and stack state partway through a
  run. Every breakpoint walk on this page ($sp= dropping 8 per call,
  =$ra= flipping between the parked and stale values, =$s4= wiped then
  restored) is that drill with the kernel as the answer key.
