So far: Multi-Cycle and the Pipeline overlapped the five stages so one instruction retires every cycle, and The Single-Cycle Datapath built the rooms the pipeline reuses. Put five instructions in those rooms at once and they start colliding. This page: the three collision types, the two hardware fixes the course pipeline ships, and what each fix costs in cycles.

One honest limit before anything runs. Our kernel executes one instruction at a time, so it cannot show pipeline timing. Every block below runs for real, and each run proves what the program computes. The cycle-by-cycle story lives in the tables on this page and in DrMIPS: the four pipeline definitions in the course lab folder are the ground truth for how this machine handles hazards, and the DrMIPS simulator source pins down what each unit computes. * Three ways a pipeline breaks

Mental model: a pipeline is a conveyor belt through five rooms, and an instruction enters a room every cycle whether or not it belongs there. Hazards are the moments when that blind rhythm goes wrong. There are exactly three kinds [textbook-grounded, P&H 4.5-4.8]:

- Structural hazard: two instructions want the same piece of hardware in the same cycle.
- Data hazard: an instruction wants a value that an earlier instruction has not produced yet.
- Control hazard: the fetch stage does not know yet where a branch goes, so it fetches a guess.

| hazard | the question it asks | the course pipeline's answer |
| structural | can two instructions share a unit in one cycle? | split the units: two memories, half-cycle register file |
| data (RAW) | is the operand ready when EX needs it? | forwarding unit, plus one stall for load-use |
| control | where does the PC go after a branch? | compare in EX, redirect at the MEM boundary, flush the wrong path |

The rest of the page takes these three rows in order, then prices them in cycles.

* Structural hazards: two instructions, one room

Mental model: with five instructions in flight, the oldest is writing results while the youngest is still being decoded, and both reach for the register bank in the same cycle. Meanwhile the fetch stage wants instruction memory at the exact moment a load wants data memory. A structural hazard is a room booked twice [textbook-grounded, P&H].

The register bank collision is real but cheap to kill. The bank has three ports: read register 1, read register 2, and one write port. The Single-Cycle Datapath page quoted L6 on this: very costly, but fast, and reading and writing the same register in one cycle needs extra logic. The fix is to split the cycle: writes land in the first half, reads sample in the second half [textbook-grounded, P&H]. An instruction in WB and an instruction in ID can then touch the same register in the same cycle, and ID still reads the fresh value. The course's DrMIPS register bank implements exactly this; its built-in description says it forwards the written value to the outputs when the same register is read and written in one cycle, and the DrMIPS Registers tab paints such a register yellow, meaning read and written in the same cycle.

The memory collision is killed by geography. Each course memory has one port shared by reads and writes: =MemRead= or =MemWrite=, never both in a cycle. In the pipeline, the IF stage of one instruction and the MEM stage of another run in the same cycle, so a single shared memory would be wanted twice. The single-cycle design already split instruction memory from data memory for exactly this reason — no functional unit can be used twice in one clock cycle — and the pipeline inherits the split for free.

The exam angle: the register bank is not a structural hazard because it has three ports plus the half-cycle write and read split; one unified memory would be a structural hazard because it has a single port and two simultaneous users. The port count is L6 material; the pipeline framing is textbook.

* Data hazards: the register is not ready yet

Mental model: reads happen early, in ID; writes happen late, in WB. Overlap an early reader with a late writer of the same register and the reader gets a stale value. The consumer knocks before the producer has put anything in the drawer.

The formal names are read-after-write (RAW), write-after-read (WAR), and write-after-write (WAW) [textbook-grounded, P&H 4.7]. In this pipeline every instruction reads its registers in ID and writes in WB, both in program order, so only RAW can occur: reads are always the earliest act, writes always the latest, and nothing overtakes anything. Expect a true-statements question built on exactly that sentence.

Here is the canonical RAW pair as code. The producer makes =$t0=; two consumers behind it read =$t0= at different distances:

#+NAME: raw-pair
#+BEGIN_SRC mips
# raw-pair.asm — a read-after-write dependence the pipeline must honor
        .text
main:   li      $s0, 20                 # a = 20
        li      $s1, 12                 # b = 12
        add     $t0, $s0, $s1           # producer: $t0 = a + b (32)
        sub     $t1, $t0, $s1           # consumer one behind: reads $t0 too early
        addi    $t2, $t0, 5             # consumer two behind: forwarded from MEM/WB
        move    $a0, $t0                # print the produced value
        li      $v0, 1                  # syscall 1: print int
        syscall
        li      $a0, '\n'               # newline between the three numbers
        li      $v0, 11                 # syscall 11: print char
        syscall
        move    $a0, $t1                # print what the 1-behind consumer got
        li      $v0, 1
        syscall
        li      $a0, '\n'
        li      $v0, 11
        syscall
        move    $a0, $t2                # print what the 2-behind consumer got
        li      $v0, 1
        syscall
        li      $v0, 10                 # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:32
:20
:37

Run it, then look at the Registers panel: =$t0= = 0x00000020, =$t1= = 0x00000014, =$t2= = 0x00000025. The Output panel prints 32, 20, 37. The interpreter hides the hazard completely, because nothing overlaps and nothing can go stale.

Now set a breakpoint on the =sub= line and Run. The machine pauses before =sub=, and the Registers panel already shows =$t0= = 0x00000020. That pause is the whole hazard in one picture. In the pipeline at that same instant, with =sub= entering EX, the new =$t0= is still inside the EX/MEM pipeline register; the register bank will not see it until the next cycle. The value exists. It is in the wrong room, and the consumer is short on time, not on data.

The stage table for the pair, with the fix the hardware actually uses:

| instruction | c1 | c2 | c3 | c4 | c5 | c6 |
| add $t0,$s0,$s1 | IF | ID | EX | MEM | WB | |
| sub $t1,$t0,$s1 | | IF | ID | EX | MEM | WB |

The consumer's EX is cycle 4. Track the new =$t0= through the same cycles:

| cycle | where the new $t0 value lives | what the sub is doing |
| 3 | ALU output at the end of EX, latched into EX/MEM | ID: reads the register bank, two cycles too early |
| 4 | the EX/MEM pipeline register | EX: the forwarding mux picks it up here |
| 5 | the register bank, written in the first half of WB | done; nothing needs it anymore |

Without forwarding, the only correct option is to wait: the consumer's ID read must land in cycle 5, which costs two stall cycles, and then the half-cycle register bank trick hands the value over [textbook-grounded, P&H 4.7]. The course's hazard-detection-only DrMIPS variant does not even stall for this pair — its unit reacts only to loads — so there the =sub= computes with the stale =$t0= and the program prints a wrong number. You will watch that happen in the lab section below.

* Forwarding: pass it over the fence

Mental model: the value the consumer needs is not lost. It is one fence away, sitting in a pipeline register that is about to carry it toward the register bank. Instead of waiting for the round trip, wire those registers back to the ALU inputs and pick the newer value. Forwarding is plumbing, not waiting.

The course pipeline's forwarding unit takes six inputs — =EX/MEM.RegWrite=, =EX/MEM.Rd=, =MEM/WB.RegWrite=, =MEM/WB.Rd=, =ID/EX.Rs=, =ID/EX.Rt= — and produces two 2-bit selects. Its logic, read from the DrMIPS source:

#+BEGIN_SRC text
ForwardA = 2  if EX/MEM.RegWrite and EX/MEM.Rd != 0
              and EX/MEM.Rd == ID/EX.Rs
         = 1  else if MEM/WB.RegWrite and MEM/WB.Rd != 0
              and MEM/WB.Rd == ID/EX.Rs
         = 0  otherwise: take the value read from the register bank

ForwardB = the same three cases, with ID/EX.Rt
#+END_SRC

Each ALU operand then passes through a 3-input mux (=MuxFwdA=, =MuxFwdB=). Input 0 is the register value captured back in ID. Input 1 is the value being written back this cycle from MEM/WB, after the =MemToReg= mux, so it covers ALU results and loaded data alike. Input 2 is the ALU result held in EX/MEM.

Every clause of that unit is an exam question:

- =$zero= is excluded: =nop= is =sll $zero,$zero,0=, so a bubble carries destination field 0, and register 0 never changes anyway.
- =RegWrite= gates it: =sw=, =beq= and flushed bubbles carry meaningless destination fields; a unit that matched fields without this gate would forward garbage.
- EX/MEM has priority: when both EX/MEM and MEM/WB hold the same register number, the EX/MEM write is the newer one.

What forwarding fixes, in one table. Distance is how far ahead the producer sits:

| producer | distance | value sits where at the consumer's EX | mux input | cost |
| ALU op | 1 | EX/MEM, its ALU result | 2 | 0 |
| ALU op | 2 | MEM/WB, its result heading to write-back | 1 | 0 |
| load | 2 | MEM/WB, its loaded data heading to write-back | 1 | 0 |
| any | 3 | register bank, written during the consumer's ID cycle | 0 | 0 |
| load | 1 | still inside data memory | none | 1 stall |

Four of the five rows cost nothing. The last row is the one forwarding cannot fix, and it gets its own section.

One more thing the table quietly says: forwarding feeds branch comparisons too. The =beq= and =bne= compare happens at the same EX-stage ALU behind the same muxes — though note the course's pipeline variants, on the =default-no-jump= set, implement only =beq=; the =bne= below is the kernel's spelling of the same compare — so a branch whose condition register was just written is forwarded like any other operand. Keep that in mind for the loop below.

* Load-use: the one stall you cannot avoid

Mental model: a load's value is the last thing to arrive in the whole machine. It steps out of data memory at the end of the load's MEM stage, and a dependent instruction right behind it wants that value at the start of its own EX — the same cycle. No wire can carry a value from the end of a cycle to the beginning of that same cycle. Forwarding cannot break causality.

#+NAME: load-use
#+BEGIN_SRC mips
# load-use.asm — the one hazard forwarding alone cannot fix
        .data
vals:   .word   111, 33                 # vals[0]=111, vals[1]=33, little-endian
        .text
main:   li      $t2, 7                  # second operand, ready long before
        la      $s1, vals               # $s1 = address of vals (2 words, uses $at)
        lw      $t0, 0($s1)             # producer: $t0 leaves memory only in MEM
        add     $t1, $t0, $t2           # consumer one behind: EX wants $t0 now
        move    $a0, $t0                # print the loaded word
        li      $v0, 1                  # syscall 1: print int
        syscall
        li      $a0, '\n'               # newline between the two numbers
        li      $v0, 11                 # syscall 11: print char
        syscall
        move    $a0, $t1                # print the sum (111 + 7)
        li      $v0, 1
        syscall
        li      $v0, 10                 # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:111
:118

Run it and read the panels. The .data hexdump starts with 6f 00 00 00 21 00 00 00: that is 111 then 33, little-endian, exactly what the =.word= line laid down. The Registers panel shows =$t0= = 0x0000006f and =$t1= = 0x00000076, which is 118 = 111 + 7. The Output panel prints 111 and 118.

Notice that this program holds two dependences and only one is a problem. The =la= writes =$s1= and the very next =lw= uses =$s1= as its base: an ALU result feeding an address, forwarded for free through input 2 of the mux. But the =lw= writes =$t0= and the very next =add= uses =$t0= as data, and that one cannot be forwarded. Same distance, different arrival time; the difference is entirely where the value is born.

The hardware that catches the second case is the hazard detection unit. Its condition, from the DrMIPS source:

#+BEGIN_SRC text
Stall = ID/EX.MemRead
        and (ID/EX.Rt == IF/ID.Rs  or  ID/EX.Rt == IF/ID.Rt)
#+END_SRC

Read it as a sentence. The instruction in EX, whose fields live in ID/EX, is a load, so =MemRead= is 1; its destination is =Rt=. The instruction in ID, whose fields live in IF/ID, names one of those same registers as =Rs= or =Rt=. Both of the consumer's fields must be checked because the second operand of an =add=, the data of an =sw=, and the second comparand of a =beq= all live in =Rt=.

When the condition fires, three things happen at once for one cycle. The PC and the IF/ID register stop writing — their =Write= inputs go low, so fetch and decode hold still — and ID/EX is flushed, which zeroes it and inserts a NOP into EX. Then the pipe moves again:

| instruction | c1 | c2 | c3 | c4 | c5 | c6 | c7 |
| lw $t0,0($s1) | IF | ID | EX | MEM | WB | | |
| add $t1,$t0,$t2 | | IF | ID | ID, held | EX | MEM | WB |
| bubble in EX | | | | EX | | | |

Cycle 5 is the payoff. The load is in WB and the =add= is in EX, so the MEM/WB to EX forward, mux input 1, hands the loaded 111 straight to the ALU. The stall and the forward cooperate: the stall buys exactly the one cycle that turns an impossible forward into an easy one.

There is also a software version of the same fix. Put any independent instruction between the =lw= and its use and the hazard vanishes: by the time the consumer reaches EX, the load has reached MEM/WB, and row three of the forwarding table applies at cost zero. Compilers do this constantly; it is called scheduling, and it is the compiler's job because the hardware stall is the expensive fallback.

The exam angle: given a sequence, count the stalls. A =lw= followed by a use of the loaded register: one stall. A =lw=, one independent instruction, then the use: zero. An =add= followed by a use: zero with forwarding, two without it, and a wrong answer in the course's detection-only variant. Check which machine the question means before writing a number.

* Control hazards: the PC is guessing

Mental model: the fetch stage knows exactly one address, PC+4, and it keeps fetching that while a branch travels down the pipe, because the compare has not happened yet. Every instruction fetched before the branch decides is a guess. If the branch is taken, the guesses must die.

#+NAME: loop-flush
#+BEGIN_SRC mips
# loop-flush.asm — a loop whose taken branches cost flush slots
        .text
main:   li      $s0, 5                  # i = 5, counts down to 1
        li      $s1, 0                  # sum = 0
again:  move    $a0, $s0                # print i
        li      $v0, 1                  # syscall 1: print int
        syscall
        li      $a0, '\n'               # newline between the numbers
        li      $v0, 11                 # syscall 11: print char
        syscall
        add     $s1, $s1, $s0           # sum += i
        addi    $s0, $s0, -1            # i-- ; the bne below needs this at once
        bne     $s0, $zero, again       # taken 4 times, falls through once
        move    $a0, $s1                # print the sum (15)
        li      $v0, 1
        syscall
        li      $v0, 10                 # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:5
:4
:3
:2
:1
:15

Run it: the Output panel counts down 5, 4, 3, 2, 1 and prints the sum 15. Two things live in this loop. The =addi= writes =$s0= and the very next =bne= compares =$s0=, a data hazard feeding a control decision, and the same forwarding muxes fix it because the branch compares at the EX-stage ALU. And the =bne= itself is taken four times and falls through once: four guesses were wrong, one was right.

Now the course pipeline's exact branch machinery, read off the =pipeline.cpu= definition. The compare happens in EX: the ALU subtracts the two registers and produces =Zero=, while the branch adder computes the target =PC+4 + (offset << 2)=. Then =Zero=, the =Branch= control bit and the target all ride the EX/MEM register, so the decision is applied one stage later, while the branch sits in MEM. There the same And gate you met as PCSrc on The Control Unit page fires, now fed from =EX/MEM.Zero= and =EX/MEM.Branch=. Its output, =PCSrc=, steers the PC mux to the target, and on the same clock edge the pipe flushes everything behind the branch. EX/MEM.Flush kills the instruction in EX. The flush Or gate, the same gate that serves the stall path, kills the instruction in ID. IF/ID.Flush kills the instruction being fetched.

| instruction | c1 | c2 | c3 | c4 | c5 | c6 | c7 |
| bne, taken | IF | ID | EX | MEM | WB | | |
| wrong-path +1 | | IF | ID | EX, killed | | | |
| wrong-path +2 | | | IF | ID, killed | | | |
| wrong-path +3 | | | | IF, killed | | | |
| branch target | | | | | IF | ID | EX |

Count the cost. The target would enter IF in cycle 2 if the branch were decided instantly; here it enters in cycle 5. A taken branch costs 3 lost slots in this design, because three younger instructions are in flight when the decision lands. An untaken branch costs nothing: the fall-through guesses were right, =PCSrc= stays 0, and nothing is flushed.

The number 3 belongs to this design — and this design is in fact the textbook default: P&H, the course text, resolves branches at the MEM boundary with penalty 3, exactly this machine. Resolve the branch one stage earlier, in EX, and only two younger instructions are in flight — an intermediate design some treatments use, penalty 2. Push the compare into ID with an extra comparator and an earlier target adder, and the penalty drops to 1 [textbook-grounded, P&H 4.8-4.9]. Real MIPS as originally defined takes a third route: the instruction after a branch always executes, a delay slot, so the ISA itself absorbs the penalty. Our kernel does not work that way — a taken branch moves the PC at once — and neither do the course pipelines, which flush instead. The fourth route is branch prediction: guess, keep going, recover when wrong [textbook-grounded]. The exam-proof rule: the taken-branch penalty equals the number of younger instructions in flight when the stem says the branch resolves.

This is also why compilers unroll loops [textbook-grounded]. A loop's branch is taken most of the time, so every iteration pays the flush. Unroll the body four times and one branch now carries four iterations of work, so the same flush slots amortize over four times the instructions. Unrolling also lengthens straight-line code, which gives the scheduler more room to fill load-use gaps with independent work. Both hazards on this page, one compiler trick.

Price our own loop. The run retires 52 instructions, the =bne= is taken 4 times, and 4 × 3 = 12 slots are flushed. Ignoring the pipeline's 4-cycle fill, that is 52 + 12 = 64 issue cycles for 52 instructions, an effective CPI of 64/52, about 1.23 for this exact program. One instruction per cycle is the best case, not the default.

* What hazards cost: effective CPI

Mental model: the ideal pipeline retires one instruction per cycle, so the effective CPI is 1 plus stall cycles per instruction plus flush cycles per instruction. Every bubble and every squashed slot is a cycle in which nothing retires. This is the same arithmetic as the performance questions on the midterm set — CPU time = IC × CPI × clock period — except the CPI is now earned the hard way.

Worked example, in the exam's own style. Loads are 20% of instructions and half of them feed a use at distance 1. Branches are 15% of instructions and half of those are taken.

| source of loss | rate | penalty | CPI added |
| load-use stalls | 0.20 × 0.5 = 0.10 | 1 | 0.100 |
| taken-branch flushes | 0.15 × 0.5 = 0.075 | 3 | 0.225 |

Effective CPI = 1 + 0.100 + 0.225 = 1.325 on the course pipeline. At 1 GHz with one million instructions, CPU time is 10^6 × 1.325 cycles on a 10^9 Hz clock, which is 1.325 ms. The unit is where the points leak: the distractor answers are decimal-place slips, at 1.325 microseconds or 13.25 ms.

Run the same instruction mix on the other branch designs and only the branch term moves. Penalty 2 gives CPI 1.25 and 1.25 ms; penalty 1 gives CPI 1.175 and 1.175 ms. Read the penalty off the design described in the stem before touching any arithmetic — that reading step is the actual question.

The exam angle, A15 style: multiply each hazard's rate by its penalty, sum the products onto 1, convert to time with the instruction count and the clock rate, and state the units. If the question asks how much faster, the ratio is the larger time over the smaller time.

* The DrMIPS variants your labs toggle

Mental model: the lab folder ships the same pipeline four times, each with one piece of the fix removed. Loading them in order is watching the machine get worse, then watching it get better.

| file | hazard detection | forwarding | what you see |
| pipeline.cpu | load-use unit | both paths | correct results; one bubble per load-use; taken branches squash three slots |
| pipeline-hazard-detection-no-forwarding.cpu | load-use unit | none | stalls appear, but RAW pairs still read stale registers: wrong results |
| pipeline-no-hazard-detection.cpu | none | none | no stalls and no flushes at all; wrong-path instructions after a taken branch run to completion: wrong results |
| pipeline-two-stage-hazard-detection-no-forwarding.cpu | custom two-stage unit | none | many more bubbles, also for plain ALU pairs, but the results come out right |

What you literally see, variant by variant:

- =pipeline.cpu=: the datapath grows a ForwardingUnit box, six inputs and two 2-bit outputs, feeding the two 3-input muxes at the ALU operands, plus the HazardDetectionUnit. Run the load-use pair from this page and the Stall wire stops being gray for one cycle; hovering the PC and IF/ID shows them holding the same values two cycles in a row, and ID/EX shows zeroed outputs, which its own description calls inserting a NOP.
- =pipeline-no-hazard-detection.cpu=: both unit boxes and both forwarding muxes are gone. The And gate still redirects the PC when a branch is taken, but nothing behind the branch is flushed, so the three wrong-path instructions execute and write back. Feed it a taken branch followed by a store and watch the store land.
- =pipeline-hazard-detection-no-forwarding.cpu=: the HazardDetectionUnit and the stall wiring are back; the forwarding hardware is not. The load-use pair stalls — you can watch the same held PC and zeroed ID/EX — and the consumer still computes with the stale register, because one stall is only enough when a forward follows it. Plain ALU pairs neither stall nor forward. The manual's warning, maybe giving wrong results, is about exactly this.
- =pipeline-two-stage-hazard-detection-no-forwarding.cpu=: a course-custom unit; upstream DrMIPS does not have it. Its input list is far richer: =IF/ID.Rs= and =IF/ID.Rt=; =ID/EX.Rt=, =Rd=, =RegWrite=, =MemRead=, =RegDst= and =OpCode=; and =EX/MEM.Rd=, =RegWrite= and =MemRead=. The natural reading of those names — inferred from the signals, not documented — is that it watches producers in both the EX and MEM stages and stalls for every RAW dependence, not only load-use. That is how it produces correct results with no forwarding at all: it pays bubbles instead.

The Assembled tab colors every instruction by stage — blue IF, green ID, yellow EX, red MEM, magenta WB — so you can watch an instruction climb the pipe one color per cycle. The Datapath tab grays wires whose values are irrelevant in the current cycle and shows yellow tips that themselves display the live values — hover a tip and it reveals the wire's identifier — and the Statistics view reports the clock frequency and the CPI it measured.

All four variants run the same instruction set, =default-no-jump=: =add=, =addi=, =and=, =beq=, =lw=, =nop=, =nor=, =or=, =slt=, =sub=, =sw=. There is no =j= anywhere, because dropping the jump keeps the PC mux branch-only — which is why this page never needed a jump flush. The lab folder also holds three progressive drafts of the two-stage variant; they are the course authors iterating on that custom unit.

That table is the Labs 3 and 4 drill sequence: see it broken, see it stall and stay wrong, see it stall correctly, see it barely stall at all.

* Exam drills this page prepares you for

- A15, performance arithmetic: the effective CPI example is the A15 method with pipeline causes — rate times penalty for each hazard, summed onto ideal CPI 1, then converted to CPU time with the instruction count and clock rate. The unit conversion is the graded trap.
- A8-style theory, choose the true statements: only RAW can occur in the five-stage in-order pipeline; forwarding cannot fix a distance-1 load-use; the hazard unit compares =ID/EX.Rt= against both =IF/ID.Rs= and =IF/ID.Rt=; the forwarding unit gates on =RegWrite= and excludes =$zero=; the taken-branch penalty equals the number of younger instructions in flight when the branch resolves.
- ILO6 and Labs 3 and 4: given one of the four variants, predict stalls, wrong values or flushes before pressing Run. The table above is the checklist.
- Hazard-spotting on real programs: take any loop from Branches, Loops, and C Translation, mark every RAW pair and every branch, and count stalls and flushes under the course design. The Exam Gym collects drills of exactly this shape.
