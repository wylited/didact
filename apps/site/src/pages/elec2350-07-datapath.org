#+TITLE: ELEC2350 · 7 · The Single-Cycle Datapath
#+SUBTITLE: Walk =add=, =lw=, =sw=, =beq= and =j= through the same rooms, one clock cycle each

So far this series has treated the processor as a given: The Machine Model
gave you the fetch-decode-execute loop, and Machine Code: R, I, J showed
that every instruction is 32 bits in one of three shapes. This page crosses
to the other side of the course: how hardware executes those bits. We build
the single-cycle processor of Lecture 6 — every instruction finishes in one
clock cycle — and walk one small program per instruction class through it.
The datapath is five stories told by the same rooms, and the kernel is the
tour guide: it stops a program right before any instruction you choose, and
its panels show exactly what that instruction's one cycle committed.

* From specification to architecture

Hardware design starts from a specification — what the chip must do, under
constraints such as performance, power, and cost (L6 Part I). The first
design step is the architecture: a set of functional units and the wires
that interconnect them, one specific job per unit. Later steps refine each
unit down through logic gates to a mask set, but the big decisions are made
at the architecture level. Our specification is deliberately small: run a
subset of MIPS — the arithmetic-logical instructions =add=, =sub=, =and=,
=or=, =slt=, the memory-reference instructions =lw=, =sw=, and the
control-flow instructions =beq=, =j= — listed on L6 p.13. Each instruction
takes one clock cycle (L6 pp.40, 54). The DrMIPS =unicycle.cpu= you will
drive in Labs 3–4 implements that subset plus =addi=, =nor= and =nop=.
The rest of this page is the architecture that satisfies the spec.

* The rooms: functional units

Mental model first. The datapath is a building. A few rooms store state:
the program counter, the register file, data memory. The corridors between
them are combinational logic — adders, the ALU, shifters, the sign-extender,
muxes — wiring that reacts to whatever is presented at its inputs and
remembers nothing. During one clock cycle every corridor is live at once,
because hardware is concurrent by nature. At the clock edge, each state
room either takes in one new value or keeps its old one. An instruction is
a tour: which rooms it visits and which corridors it walks is exactly what
tells =add= from =lw= from =j=.

| Unit | Kind | Its job |
|---+---+---|
| PC | state | 32-bit register holding the address of the instruction that owns the current cycle; changes only at a clock edge. |
| Instruction memory | combinational | Returns the 32-bit instruction word stored at the address the PC supplies. |
| Register file | state, 3 ports | Holds all 32 registers; two read ports serve numbers continuously, and one write port listens for a write-enable. |
| Sign-extend | combinational | Widens the instruction's 16-bit immediate to 32 bits by copying bit[15] into the top 16 positions. |
| ALU | combinational | Computes and, or, nor, add, sub, slt and the Zero flag — the machine's only general calculator. |
| PC+4 adder | combinational | Always computes the address of the next sequential instruction. |
| Branch shift-left-2 | combinational | Multiplies the sign-extended 16-bit branch offset by 4, turning a count of words into a byte distance. |
| Branch adder | combinational | Computes the branch target PC+4 + (offset × 4). |
| Jump shift-left-2 | combinational | Appends two zero bits to the 26-bit jump field, widening it to 28 bits. |
| Data memory | state, one port | Holds the program's data; reads for lw or writes for sw — one direction per cycle, never both. |
| Muxes | combinational | Choose between two wires wherever one instruction class needs source A and another needs source B. |

Two state rooms deserve a closer look. The register file has three ports —
read register 1, read register 2, and a write port with a write-enable — so
it can read two registers and write a third in the same cycle; the lecture
calls this "very costly but fast" (L6 pp.34–36). Instruction memory and
data memory are separate units. Instruction memory is read-only —
combinational, with no write port at all — while data memory has a single
port for both reading and writing, so within one cycle it can do one or
the other, never both (L6 p.37). Fetching an instruction while a load
reads its data word is possible only because there are two memories.

** State changes only at the clock edge

A combinational element's output is a pure function of its current inputs —
AND gate, adder, mux, ALU, sign-extend. A sequential element stores
information: its output updates only at a clock edge, and a register with a
write control updates only at an edge where write is 1 (L6 pp.27–31). The
clock exists to tame concurrency: all the gates are always computing, and
the clock marks the instants where we agree the results are stable. A clock
period must be long enough for the slowest chain of logic to settle — the
longest delay determines the clock period (L6 p.32).

In this machine the state elements are the =PC=, the register file, and
data memory: the three things a program run can change. Everything else
settles some time inside the cycle. The single-cycle discipline is that all
writes commit together at the end of the cycle: the register write of an
=add=, the memory write of an =sw=, and the new =PC= all land at the same
edge. L6 p.40 words it as the write-back happening "only at the next clock
edge". One edge, one instruction, all state updated at once.

That is why the kernel's Step button is an honest model of a clock cycle.
One Step executes exactly one machine instruction and then shows you what
the edge committed: the =Registers= panel flags the register that was
written, the =hi · lo · pc= panel flags =pc= when a branch or jump moved
it, and the =.data= hexdump shows memory writes. The kernel is an
interpreter, not a clocked circuit — but per instruction, its
before-and-after state is precisely the single-cycle machine's edge.

* Fetch: every cycle starts the same

Every cycle begins identically, whatever the instruction. The =PC= drives
the instruction memory's address input; the memory returns the 32-bit
instruction word; and at the same time the PC+4 adder computes the next
sequential address. Fetch is class-blind — no opcode has been examined yet.
The PC+4 result is needed even by =beq= and =j=: it is the default next
=PC=, the base of every branch target, and the source of the top four bits
of a jump target.

#+BEGIN_SRC text
Common to all instructions (L6 p.19)
  1. Fetch an instruction from memory based on PC
  2. Decode; read registers if necessary
  3. Execute — ALU for arithmetic-logical instructions,
     ALU address computation for loads and stores,
     adders and shifters for branch destinations
  4. Access memory if it is a load or store
  5. Write back a result to a register if necessary
  6. Update PC: PC + 4, or the address that a branch
     or jump instruction specifies
#+END_SRC

In the kernel, the Program panel marks the row at =pc= as current, and that
row's bytes column is the encoded word instruction memory returns. In the
five walks below, the bytes column is our instruction-register window: every
address, field and immediate the narrations quote is sitting right there on
the row, and every encoding was read off this kernel's assembler.

* An R-type walk: =add $t0, $s1, $s2=

An R-type instruction never leaves the register-file neighborhood: read two
registers, compute, write one register. No immediate, no data memory, no
target arithmetic — the shortest tour of the building, which is why the
lecture starts there, with exactly this instruction and exactly these
register values (L6 pp.14, 44).

#+BEGIN_SRC text
add reg1, reg2, reg3 (L6 p.14)
  1. Fetch the instruction from memory based on PC
  2. Decode the instruction to know its operation
  3. Read register reg2 and reg3
  4. Execute the addition to get reg2 + reg3
  5. Write back the result into reg1
sub, and, or, slt are similar; only the execution step differs.
#+END_SRC

#+NAME: add-walk
#+BEGIN_SRC mips
# rtype-walk.asm — the lecture's add $t0, $s1, $s2 (L6 slide 44), runnable
        .text
main:   li      $s1, 100                # s1 = 100: li is really addiu, one word
        li      $s2, 200                # s2 = 200
        add     $t0, $s1, $s2           # t0 <- s1 + s2 = 300
        move    $a0, $t0                # a0 <- t0: argument for print
        li      $v0, 1                  # syscall 1: print int in $a0
        syscall
        li      $v0, 10                 # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:300

Fetch. The =PC= holds =0x00400008=. Instruction memory returns =0x02324020=;
the Program panel shows its bytes as =02 32 40 20= on the =add= row. Split
into fields that is =000000 10001 10010 01000 00000 100000= — opcode 0,
=rs= 17, =rt= 18, =rd= 8, shamt 0, funct 32 — the lecture's slide-44
encoding, field for field. How those bits split is the subject of Machine
Code: R, I, J; here we watch what the hardware does with them.

Decode and register read. Opcode 0 says R-type, so control prepares
=RegWrite= and the write port will listen to =instr[15:11]=. Read port 1
takes =instr[25:21]= = 17 and returns =$s1= = 100. Read port 2 takes
=instr[20:16]= = 18 and returns =$s2= = 200. Both reads are mux lookups
inside the register file and finish well before the edge.

Execute. The ALU adds: =100 + 200 = 300=. For this instruction the ALU's
Zero output, the sign-extender, data memory, and both target units are
unused.

Write-back. The write port takes =instr[15:11]= = 8 (=rd=, =$t0=), the
write data is the ALU result, and =RegWrite= is 1. The value waits at the
register file's write port; at the clock edge, =$t0= becomes 300. The next
=PC= was computed as =PC+4= back at fetch, and nothing overrides it.

Watch the whole cycle commit. Click the gutter line number on the =add=
line (line 5 of the block) to set a breakpoint, then Run: the machine
pauses with the =add= row current and the =hi · lo · pc= panel showing
=pc= at =0x00400008=. Step once — that single Step is the whole cycle. Look
at the =Registers= panel: =$t0= is flagged =changed=, value =0x0000012c=
with 300 in the decimal sub-display, and nothing else moved. Run to the end
and the Output panel prints 300. The =li= rows at the top are =addiu= in
disguise; they only load the lecture's slide-44 values into =$s1= and
=$s2=.

* A load walk: =lw $t0, 4($s1)=

A load is the longest tour in the building, and the only one that visits
every major room: the register file, the sign-extender, the ALU, data
memory, and the write-back mux — then the register file again, this time as
a writer. The one new idea: the ALU is re-hired as an address adder (L6
pp.15, 45–46).

#+BEGIN_SRC text
lw reg1, const(reg2) (L6 p.15)
  1. Fetch the instruction from memory based on PC
  2. Decode the instruction to know its operation
  3. Read register reg2
  4. Execute: address = reg2 + sign-extended const
     (const is a 16-bit signed number)
  5. Access memory: read the data at that address
  6. Write back the data into reg1
#+END_SRC

#+NAME: lw-walk
#+BEGIN_SRC mips
# lw-walk.asm — lw crosses the whole datapath, data memory included
        .data
array:  .word   7, 50                   # array[0]=7, array[1]=50
        .text
main:   la      $s1, array              # s1 <- 0x10010000 (la = lui+ori, 2 rows)
        lw      $t0, 4($s1)             # t0 <- Mem[s1 + 4] = 50
        move    $a0, $t0                # print the word that was loaded
        li      $v0, 1
        syscall
        li      $v0, 10                 # exit
        syscall
#+END_SRC

#+RESULTS:
:50

Fetch. =pc= is =0x00400008=; the bytes column of the =lw= row reads
=8e 28 00 04=, the word =0x8e280004=. Fields: opcode =35= (=lw=), =rs= 17
(the base), =rt= 8 (the destination), immediate =4=.

Decode and register read. Read port 1 takes 17 and returns =$s1= =
=0x10010000= — the two =la= rows above loaded it, and both listing rows
point at that one source line. Read port 2 dutifully reads =instr[20:16]=
= 8 as well, because the register file always drives both ports; this
cycle the ALU's input mux ignores it and picks the immediate instead.

Execute: address computation. The sign-extend unit copies bit[15] of the
immediate into the top 16 bits: =0004= becomes =0x00000004= (had the
offset been negative, those copies would be 1s). The ALU adds:
=0x10010000 + 4 = 0x10010004=. That sum is not data — it is a data memory
address.

Memory. =MemRead= is 1; data memory reads the word at =0x10010004= and
returns 50.

Write-back. Now the write-back mux has a real decision: its two inputs are
the ALU result (the address, not wanted) and the data memory word (the
payload). =MemtoReg= is 1, so memory data wins. The write port listens to
=rt= = 8 this time, not =rd= — which field the write port follows is the
=RegDst= mux, a preview of The Control Unit. At the edge, =$t0= ← 50.

Breakpoint the =lw= line (line 6), Run, Step. The =Registers= panel flags
only =$t0=, now 50; =pc= advanced to =0x0040000c= without a flag, because
the next =PC= is the sequential one. Loads read memory without changing
it: the first eight bytes of the =.data= hexdump read =07 00 00 00 32 00
00 00= — =array[0]= = 7 and =array[1]= = 50, little-endian, exactly as
Loads, Stores, and the Byte Addressed World taught.

* A store walk: =sw $t0, 0($s1)=

A store is a load with the data flowing the other way, minus the
write-back. It is the only walk that writes data memory — like =beq=, it
reads two registers and writes none (L6 p.16).

#+BEGIN_SRC text
sw reg1, const(reg2) (L6 p.16)
  1. Fetch the instruction from memory based on PC
  2. Decode the instruction to know its operation
  3. Read registers reg1 and reg2
  4. Execute: address = reg2 + sign-extended const
  5. Access memory: store reg1's data at that address
     (the store happens at the next clock edge)
#+END_SRC

#+NAME: sw-walk
#+BEGIN_SRC mips
# sw-walk.asm — sw writes data memory; read it back to prove it
        .data
slot:   .word   1111                    # about to be overwritten by the store
        .text
main:   la      $s1, slot               # s1 <- 0x10010000: the store's base
        li      $t0, 200                # t0 = 200: the value to store
        sw      $t0, 0($s1)             # Mem[s1 + 0] <- 200
        lw      $a0, 0($s1)             # read it back: 200
        li      $v0, 1
        syscall
        li      $v0, 10                 # exit
        syscall
#+END_SRC

#+RESULTS:
:200

Fetch. The =sw= row's bytes are =ae 28 00 00=, the word =0xae280000=:
opcode =43=, =rs= 17, =rt= 8, immediate =0=.

Decode and register read — two registers, both live. Read port 1: =17= →
=$s1= = =0x10010000=, the base. Read port 2: =8= → =$t0= = 200, the data
to store. For a store, the =rt= field names a source, not a destination.

Execute. Sign-extend =0= → =0x00000000=; the ALU adds and produces the
address =0x10010000=.

Memory. =MemWrite= is 1: data memory writes 200 to =0x10010000=, and the
write commits at the clock edge like every state change.

No write-back. =RegWrite= is 0, so nothing flows to the register file's
write port; whatever the write-back mux happens to select is ignored —
your first don't-care, an idea The Control Unit page will lean on. The next
=PC= is =PC+4=.

Breakpoint the =sw= line (line 7), Run, Step. The =Registers= panel flags
nothing at all — the store's only state change is in memory. The =.data=
hexdump row at =0x10010000= now starts =c8 00 00 00=: 200 written
little-endian. The =lw= row after the store exists only to prove the point
to the Output panel: it reads the word back and prints 200.

* A branch walk: =beq $t0, $t1, skip=

A branch does two jobs in one cycle: decide and aim. Deciding is a
comparison, and the ALU is the comparator. Aiming needs an addition —
=PC+4= plus a shifted offset — and since no functional unit may be used
twice in one cycle, that addition gets its own adder. This walk explains
why the datapath owns more adders than you might expect (L6 pp.17, 48–49).

#+BEGIN_SRC text
beq reg1, reg2, label (L6 p.17)
  1. Fetch the instruction from memory based on PC
  2. Decode the instruction to know its operation
  3. Read registers reg1 and reg2
  4. Execute: compare reg1 and reg2 for equality
  5. If equal, PC = PC + 4 + sign-extended (const × 4)
     (const is the 16-bit word offset the assembler
      computed from the label)
#+END_SRC

#+NAME: beq-walk
#+BEGIN_SRC mips
# beq-walk.asm — a taken beq skips two instructions (L6 slide 49 shape)
        .text
main:   li      $t0, 200                # t0 = 200
        li      $t1, 200                # t1 = 200: the compare will be equal
        li      $t2, 111                # marker: survives only if branch taken
        beq     $t0, $t1, skip          # taken: PC <- PC+4 + 2*4
        addiu   $t2, $zero, 222         # skipped by the branch
        addiu   $t2, $zero, 333         # skipped by the branch
skip:   move    $a0, $t2                # still 111: both adds were jumped over
        li      $v0, 1
        syscall
        li      $v0, 10                 # exit
        syscall
#+END_SRC

#+RESULTS:
:111

Fetch. The =beq= row's bytes are =11 09 00 02=, the word =0x11090002=:
opcode =4= (=beq=), =rs= 8, =rt= 9, immediate =2=. That immediate is not
data — it is the assembler's word offset from =PC+4= to the label, the
encoding you drilled on Machine Code: R, I, J.

Decode and register read. Port 1: =8= → =$t0= = 200. Port 2: =9= → =$t1=
= 200.

Execute: decide. The ALU subtracts: =200 - 200 = 0=, so its Zero output is
1. For =beq= the ALU is a comparator, and its result never reaches any
register.

Execute: aim. Concurrently, the branch shift-left-2 turns the sign-extended
offset into a byte distance (=2 × 4 = 8=) and the branch adder computes
=PC+4 + 8 = 0x00400010 + 8 = 0x00400018= — the address of =skip=. The
lecture's slide-49 example is the same arithmetic with round numbers: =beq=
at 1000 with offset 2, so the target is =1004 + 2 × 4 = 1012=, and the two
instructions at 1004 and 1008 are skipped. Here the two =addiu= rows at
=0x00400010= and =0x00400014= are the skipped pair.

Update PC. The next-PC mux chooses between =PC+4= and the branch target.
Its select is =Branch= AND =Zero=: control raised =Branch= because the
opcode is =beq=, and the ALU supplied Zero = 1. The target wins; the jump
mux behind it passes the value through unchanged.

Breakpoint the =beq= line (line 6), Run, Step. No register is flagged —
the only state a taken branch changes is the =PC=. The =hi · lo · pc=
panel flags =pc= and shows =0x00400018=. Run to the end: the Output panel
prints 111, the marker that survived, because the rows that would have
written 222 and 333 never executed. Then change the second =li= to
=li $t1, 201= and Run again: now Zero stays 0, the mux keeps =PC+4=, both
=addiu= rows execute, and the program prints 333.

* A jump walk: =j skip=

A jump is the shortest tour of all. No register is read or written, the
ALU is idle, data memory is idle — the target comes out of the fetched
instruction word itself (L6 pp.18, 50–51).

#+BEGIN_SRC text
j label (L6 p.18)
  1. Fetch the instruction from memory based on PC
  2. Decode the instruction to know its operation
  3. PC = ((PC + 4) & 0xf0000000) | (const × 4)
     (const is the 26-bit field the assembler computed
      from the label; shifted left 2, it replaces the
      low 28 bits of PC + 4)
#+END_SRC

#+NAME: j-walk
#+BEGIN_SRC mips
# j-walk.asm — j rebuilds the PC out of the instruction word itself
        .text
main:   li      $t0, 5                  # t0 = 5
        j       skip                    # PC <- {(PC+4)[31:28], field << 2}
        addiu   $t0, $t0, 100           # never executed
skip:   move    $a0, $t0                # still 5: the addiu was jumped over
        li      $v0, 1
        syscall
        li      $v0, 10                 # exit
        syscall
#+END_SRC

#+RESULTS:
:5

Fetch. The =j= row's bytes are =08 10 00 03=, the word =0x08100003=:
opcode =2= and the 26-bit field =0x100003=.

Build the target. The jump shift-left-2 appends two zero bits, =0x100003=
→ =0x40000c=, a 28-bit value. The concat unit takes the top four bits of
=PC+4= — =(0x00400008)[31:28]=, which is 0 — and wires them in front: new
=PC= = =0x0040000c=, the address of =skip=. The lecture's formula:
=PC = ((PC + 4) & 0xf0000000) | (const_num × 4)= — keep the top of =PC+4=,
replace the low 28 bits with the field shifted left 2.

What does not happen. No register port is used, the ALU output is ignored,
and even the branch adder is idle: a =j= target is absolute within its
256 MiB region, not an offset, so no addition is needed. The top-four-bits
rule is also why a =j= cannot jump outside the 256 MiB region that
contains it — the fact behind the addressing-mode questions you have seen.

Breakpoint the =j= line (line 4), Run, Step. The =Registers= panel is
quiet; the =hi · lo · pc= panel flags =pc=, now =0x0040000c= — straight
over the =addiu= at =0x00400008=. The Output panel prints 5; the skipped
instruction would have made it 105.

* The whole machine on one page

** The whole datapath as a table

Here is the complete architecture as one table: every element, and what
each of the five walked instructions does with it during its cycle.
Combinational units are always flowing; =unused= below means the muxes
ignore that output for this instruction. DrMIPS draws exactly this machine
as =unicycle.cpu= — the same elements under the names =PC=, =PCAdder=,
=InstMem=, =RegBank=, =ExtendImm=, =ALU=, =ShiftImm=, =AddBranch=,
=ShiftJump=, =DataMem= and five muxes — and grays out the unused wires in
its Datapath tab, one instruction at a time.

| Element | add $t0, $s1, $s2 | lw $t0, 4($s1) | sw $t0, 0($s1) | beq $t0, $t1, skip | j skip |
|---+---+---+---+---+---|
| PC during the cycle | 0x00400008 | 0x00400008 | 0x0040000c | 0x0040000c | 0x00400004 |
| Instruction memory | fetches the add word | fetches the lw word | fetches the sw word | fetches the beq word | fetches the j word |
| PC+4 adder | 0x0040000c, next PC | 0x0040000c, next PC | 0x00400010, next PC | 0x00400010, branch base | 0x00400008, top 4 bits |
| Register file | reads $s1, $s2; writes $t0 | reads $s1; writes $t0 | reads $s1, $t0; no write | reads $t0, $t1; no write | unused |
| Sign-extend | mux picks the register | 4 → 0x00000004 | 0 → 0x00000000 | 2 → 0x00000002 | unused |
| ALU | 100 + 200 = 300 | 0x10010000 + 4, address | 0x10010000 + 0, address | 200 - 200 = 0, Zero = 1 | unused |
| Data memory | unused | reads 50 | writes 200 | unused | unused |
| Branch shift + adder | unused | unused | unused | 2 × 4 = 8; target 0x00400018 | unused |
| Jump shift + concat | unused | unused | unused | unused | 0x100003 → 0x0040000c |
| Write-port mux (RegDst) | picks rd 8 | picks rt 8 | ignored | ignored | ignored |
| ALU input mux (ALUSrc) | register $s2 | immediate | immediate | register $t1 | ignored |
| Write-back mux (MemtoReg) | ALU result | memory data | ignored | ignored | ignored |
| Next-PC muxes | PC+4 | PC+4 | PC+4 | branch target (Branch and Zero) | jump target (Jump) |

Read the table column by column and the five stories appear: =add= stays
in the register-file neighborhood; =lw= and =sw= leave it once to visit
data memory; =beq= and =j= are all about the =PC= wiring. Read it row by
row and you see why every unit exists: each one is load-bearing for at
least one column.

** No functional unit used twice in one cycle

The single-cycle machine obeys one hard rule: no functional unit can be
used twice in one clock cycle (L6 p.54). The rule, not taste, explains the
unit list.

=beq= wants three additions in one cycle: =PC+4= (the default next =PC=
and the branch base), the branch target =PC+4 + (offset × 4)=, and the
comparison =reg1 - reg2=. One ALU cannot do all three — it is busy
subtracting — so the target gets the branch adder and =PC+4= gets its own
dedicated adder. Three additions, three separate units.

=lw= wants two memory reads in one cycle: the instruction fetch and the
data word. A single one-port memory cannot serve both, so the machine
ships two memories, instruction and data. Each of them, having one port,
can read or write per cycle but never both — the same constraint that
returns as a structural hazard when the pipeline pages revisit it.

The register file is the deliberate exception: three ports, so reading two
registers while writing a third is one cycle's work. The exception is
expensive — "very costly but fast" is the lecture's phrase — but R-type
instructions need it.

And =j= shows the payoff of the rule: it needs no ALU at all, because
its target comes from the instruction word itself. The designers did not
add a path =j= could share; they wired the shift-and-concat straight into
the next-PC mux.

** The clock pays for the slowest instruction

Every instruction gets one full clock cycle, so the cycle must be long
enough for the slowest one: the clock period is decided by the slowest
instruction (L6 p.54), because the longest delay determines the period
(L6 p.32). Walk the chains. An =add= runs instruction memory → register
file → ALU → register write. A =beq= runs instruction memory → register
file → ALU → next-PC mux, with the target adder working in parallel. A
=lw= runs instruction memory → register file → sign-extend → ALU → data
memory → write-back mux → register write: every big unit in the machine,
in one chain. The load is the classic longest path. The lecture states the
rule without crowning a winner; with DrMIPS's default latencies — data
memory 400, instruction memory 300, register file and ALU 100 each — the
load is the instruction that pays for both memories plus everything
between them, which is what the red critical path in the simulator's
performance mode shows.

That is the single-cycle design's fatal flaw. A program made entirely of
=add=s still spends a load-length cycle on every one of them; most of the
machine idles most of the time. The reward is simplicity itself: control
is a combinational function of the opcode, there is nothing to schedule,
and CPI is exactly 1 by construction. The fix — cut the cycle into stages
and let instructions overlap — is the whole subject of Multi-Cycle and the

* Exam drills this page prepares you for

This page grounds final-exam ILO5, processor design, and the DrMIPS
=unicycle.cpu= experiments of Labs 3–4. The drill archetypes it feeds:

- A8, ISA and format theory: PC semantics — what updates the =PC= and
  when; why =j= shifts its field left 2 and concatenates the upper 4 bits

  4)= and jump target = ={(PC+4)[31:28], field << 2}=, both computed here
  on real hardware with real numbers.
- A7, memory-access counting: the unit table shows that only =lw= and
  =sw= touch data memory, while every instruction reads instruction
  memory exactly once.
