#+TITLE: JavaScript's Weird Parts, Step by Step
#+SUBTITLE: Coercion, closures, hoisting, and the event loop on a single-steppable interpreter

* What this interpreter runs

This page runs a small, steppable JavaScript interpreter written in TypeScript rather than your browser's JS engine. It covers the core mechanics — =var=/=let=/=const=, functions, arrow functions, loops, =Math=, =console=, and basic array/string methods — and leaves out classes, =this=, and =async=/=await=. Anything outside the subset fails cleanly at load time with the exact line number.

As you step through a block, watch the three right-hand panels: *Scopes* (live variable bindings), *Call stack* (active function frames), and *Event loop* (microtask and macrotask queues).

* Loose (= == =) vs strict (= === =) equality

Strict equality (===) never converts types: if the types differ, the answer is =false=. Loose equality (==) converts operands using the spec's =ToPrimitive= and =ToNumber= rules until both sides have the same type:

| Comparison          | Coercion                                 | Result |
|---------------------+------------------------------------------+--------|
| ='' == 0=           | =''= becomes =0=                         | true   |
| ='1' == 1=          | ='1'= becomes =1=                        | true   |
| =[] == false=       | =[]= -> =''= -> =0=, and =false= -> =0= | true   |
| =null == undefined= | special case (equal only to each other)  | true   |
| =NaN == NaN=        | =NaN= is never equal to anything         | false  |
| =[] === false=      | none (different types)                   | false  |

That third row is the classic JS gotcha: =[]= converts to =''=, which converts to =0=, and =false= also converts to =0=. Step through the block below to see each comparison evaluate.

#+BEGIN_SRC javascript
console.log('' == 0, '1' == 1);
console.log([] == false, [] == 0, [7] == 7);
console.log(null == undefined, null == 0, undefined == 0);
console.log(NaN == NaN, NaN === NaN);
console.log([] === false, '1' === 1);
#+END_SRC

#+RESULTS:
: true true
: true true true
: true false false
: false false
: false false

Practical rule: default to === unless you deliberately want =x == null= (to match both =null= and =undefined=).

* Closures capture bindings, not snapshots

A closure holds a live reference to the variable binding in its enclosing scope — not a copy of its value at the moment the function was created:

- In the =var i= loop, there is only *one* function-scoped =i=. All three closures point to that same slot, which holds =3= once the loop ends.
- In the =let j= loop, each iteration creates a *fresh* block-scoped =j=, so each closure remembers its own number (=0=, =1=, =2=).

#+BEGIN_SRC javascript
var withVar = [];
for (var i = 0; i < 3; i = i + 1) {
  withVar.push(function () { return i; });
}
var withLet = [];
for (let j = 0; j < 3; j = j + 1) {
  withLet.push(function () { return j; });
}
console.log(withVar[0](), withVar[1](), withVar[2]());
console.log(withLet[0](), withLet[1](), withLet[2]());
#+END_SRC

#+RESULTS:
: 3 3 3
: 0 1 2

Set a breakpoint on the =console.log= lines and inspect *Scopes*: all three =withVar= functions share a single =i=, while each =withLet= function has its own =j=.

* Hoisting and the Temporal Dead Zone

Before running the first line of a scope, JavaScript scans ahead and registers every declaration:

- =var= declarations are initialized immediately to =undefined= (their assignments stay in place).
- =function= declarations are hoisted completely and can be called before they appear.
- =let= and =const= are also hoisted, but stay uninitialized until their declaration line runs — reading them early throws a =ReferenceError= (the *Temporal Dead Zone*).

#+BEGIN_SRC javascript
console.log(hoistedVar, typeof hoistedFn);
var hoistedVar = 'now set';
function hoistedFn() { return 'callable before its line'; }
console.log(hoistedVar, hoistedFn());
console.log(later);
let later = 'never reached';
#+END_SRC

#+RESULTS:
: undefined function
: now set callable before its line

Line 5 throws =Cannot access 'later' before initialization= and stops execution. Step from line 1 and watch =hoistedVar= appear in *Scopes* as =undefined= before line 1 even runs.

* The event loop: sync, microtasks, macrotasks

JavaScript executes one turn at a time in strict priority order:

- *Synchronous code* runs to completion first.
- *Microtasks* (=Promise.resolve().then(...)=) drain completely right after synchronous code finishes.
- *Macrotasks* (=setTimeout(..., 0)=) run one at a time *after* the microtask queue is empty (and any new microtasks queued by a macrotask drain before the next macrotask).

#+BEGIN_SRC javascript
console.log('1 sync');
setTimeout(function () { console.log('4 macrotask'); }, 0);
Promise.resolve().then(function () { console.log('3 microtask'); });
console.log('2 still sync');
#+END_SRC

#+RESULTS:
: 1 sync
: 2 still sync
: 3 microtask
: 4 macrotask

Put a breakpoint on line 4 and check the *Event loop* panel: even with a =0= ms timeout, the microtask always runs before the macrotask.

* Array pipelines: =filter= and =map=

=filter= and =map= take regular closures and call them once per element. Set a breakpoint inside either callback to watch a new frame push onto the *Call stack* for each element.

#+BEGIN_SRC javascript
var numbers = [1, 2, 3, 4, 5, 6];
var evens = numbers.filter(function (n) { return n % 2 === 0; });
var doubled = evens.map(function (n) { return n * 2; });
console.log(evens);
console.log(doubled);
console.log(doubled.join(' · '));
#+END_SRC

#+RESULTS:
: [ 2, 4, 6 ]
: [ 4, 8, 12 ]
: 4 · 8 · 12
