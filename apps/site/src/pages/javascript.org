#+TITLE: JavaScript, Stepped Live
#+SUBTITLE: Coercion, [[file:lisp.org::*Closures][closures]], hoisting, and the event loop on a small steppable JS interpreter

This page runs a hand-written JavaScript interpreter instead of your browser's engine, so you can single-step through statements and watch *Scopes*, *Call stack*, and *Event loop* update live. It supports =var=/=let=/=const=, functions, arrows, loops, =Math=, =console=, and basic array/string methods. Classes, =this=, and =async=/=await= are rejected up front with a line number.

* Why =[]= == =false=

=== checks type and value without converting anything. == coerces operands until their types match, which is how an empty array ends up equal to =false=: =[]= turns into =''=, =''= turns into =0=, and =false= turns into =0=.

| Expression          | What == actually does               | Result |
|---------------------+-------------------------------------+--------|
| ='' == 0=           | =''= becomes =0=                    | true   |
| ='1' == 1=          | ='1'= becomes =1=                   | true   |
| =[] == false=       | =[]= -> =''= -> =0=, =false= -> =0= | true   |
| =null == undefined= | special case in the spec            | true   |
| =NaN == NaN=        | =NaN= never equals anything         | false  |
| =[] === false=      | different types, no coercion        | false  |

Step through the calls below to see each row in action.

#+BEGIN_SRC javascript
console.log('' == 0, '1' == 1);
console.log([] == false, [] == 0, [7] == 7);
console.log(null == undefined, null == 0, undefined == 0);
console.log(NaN == NaN, NaN === NaN);
console.log([] === false, '1' === 1);
#+END_SRC

#+RESULTS:
: true true
: true true true
: true false false
: false false
: false false

* Closures hold bindings, not copies

A function remembers the scope slot a variable lives in, not the value it happened to hold when the function was defined. In the =var i= loop there is only one =i= for the whole scope, so all three functions read =3= after the loop finishes. With =let j=, each iteration gets its own slot, so they return =0=, =1=, =2=.

#+BEGIN_SRC javascript
var withVar = [];
for (var i = 0; i < 3; i = i + 1) {
  withVar.push(function () { return i; });
}
var withLet = [];
for (let j = 0; j < 3; j = j + 1) {
  withLet.push(function () { return j; });
}
console.log(withVar[0](), withVar[1](), withVar[2]());
console.log(withLet[0](), withLet[1](), withLet[2]());
#+END_SRC

#+RESULTS:
: 3 3 3
: 0 1 2

Put a breakpoint on line 9 and look at *Scopes*: the =withVar= functions all point to the same =i=, while each =withLet= function has a separate =j=.

* Hoisting and the temporal dead zone

Before executing line 1 of a scope, the interpreter registers every declaration in that scope. =var= bindings start out as =undefined=, and =function= declarations are immediately callable. =let= and =const= are registered too, but stay unreadable until their declaration line runs; touching =later= on line 5 throws =Cannot access 'later' before initialization= and halts the block.

#+BEGIN_SRC javascript
console.log(hoistedVar, typeof hoistedFn);
var hoistedVar = 'now set';
function hoistedFn() { return 'callable before its line'; }
console.log(hoistedVar, hoistedFn());
console.log(later);
let later = 'never reached';
#+END_SRC

#+RESULTS:
: undefined function
: now set callable before its line

Step from the very first line and watch =hoistedVar= show up in *Scopes* before line 1 executes.

* Event loop order: sync, microtasks, macrotasks

Top-level synchronous code runs to completion first. Once it finishes, the engine drains the entire microtask queue (=Promise.resolve().then(...)=) before taking a single macrotask (=setTimeout(..., 0)=). That is why =3 microtask= always beats =4 macrotask= even when the timeout is =0=.

#+BEGIN_SRC javascript
console.log('1 sync');
setTimeout(function () { console.log('4 macrotask'); }, 0);
Promise.resolve().then(function () { console.log('3 microtask'); });
console.log('2 still sync');
#+END_SRC

#+RESULTS:
: 1 sync
: 2 still sync
: 3 microtask
: 4 macrotask

Set a breakpoint on line 4 and check the *Event loop* panel to see both queues lined up before the body finishes.

* Stepping inside =filter= and =map=

Array methods here run inside the interpreter itself, so you can drop a breakpoint inside a callback and watch the *Call stack* push a frame for every element.

#+BEGIN_SRC javascript
var numbers = [1, 2, 3, 4, 5, 6];
var evens = numbers.filter(function (n) { return n % 2 === 0; });
var doubled = evens.map(function (n) { return n * 2; });
console.log(evens);
console.log(doubled);
console.log(doubled.join(' · '));
#+END_SRC

#+RESULTS:
: [ 2, 4, 6 ]
: [ 4, 8, 12 ]
: 4 · 8 · 12
