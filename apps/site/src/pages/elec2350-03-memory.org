#+TITLE: ELEC2350 · 3 · Loads, Stores, and the Byte-Addressed World
#+SUBTITLE: The only road between registers and memory, walked byte by byte: base+offset addressing, the ×4 rule, alignment, endianness, and what counts as a memory access

So far, The Machine Model gave you a CPU that fetches, decodes, and
executes, and Arithmetic and Logic did all of its computing inside
registers. This page crosses the only bridge between those registers and
memory: the data transfer instructions =lw= and =sw=. Memory is
byte-addressed — every byte has its own 32-bit address — and that one
fact generates everything below: why array indices scale by 4, why an
off-by-one load traps, which byte of a word lands first, and what an
examiner counts as a memory access.

Every executable block below is a real program: =.data= at =0x10010000=, =.text= at
=0x00400000=, exactly as the memory map on The Machine Model drew them.
Run them, then read the panels — the =.data= hexdump in particular is
this page's co-teacher, because loads and stores are the one subject
whose whole point is bytes you can watch move.

* Loads and stores: anatomy of a data transfer

Mental model: registers are the workbench, memory is the warehouse.
MIPS is a load-store ISA — no arithmetic instruction has a memory
operand, so a number in the warehouse reaches the workbench only by
=lw=, and a result goes back only by =sw=. Each instruction moves one
whole 4-byte word and names exactly one address.

Both instructions build that address the same way. In
=lw $t1, 8($t3)= there are three parts: =$t1= is the destination
register, =8= is the offset, and =$t3= is the base. The effective
address is the contents of the base register plus the offset:
=$t1 = Mem[$t3 + 8]=. Lecture 3 (p.58) names this Base addressing, one
of the course's five addressing modes.

The offset is a 16-bit two's-complement number, sign-extended to 32
bits before the addition. Negative offsets are legal and common:
=lw $a0, -32($sp)= reads a word 32 bytes deeper in the stack, and
encodes with immediate =0xFFE0=. The reach is ±32 KiB around the base,
since offsets run from −32768 to 32767. The base can even be =$zero=:
T2's paper example =lw $s3, 4($zero)= has effective address
=0x00000004=. T2 draws its memory pictures starting at address 0; this
kernel's data segment starts at =0x10010000=, so address =0x4= is
unmapped here — but the arithmetic transfers as is: address = 0 + 4.

=sw= uses the same address arithmetic with the data flowing the other
way, and the register field flips roles: in =sw $t1, 8($t3)= the
register =$t1= is the source and memory is the destination,
=Mem[$t3 + 8] = $t1=. For =lw= that field is a destination; for =sw= a
source. Only the direction differs; the syntax is identical.

Registers and memory are separate storages, and nothing done to a
register reaches memory until a =sw= says so. T2's trace question:
with =$t0= holding =0x1000= and =Mem[0x1008]= holding =25=, the
sequence =lw $t1, 8($t0)=, =addi $t1, $t1, 1=, =sw $t1, 8($t0)= ends
with =$t1= at =26= and =Mem[0x1008]= at =26= — but between the =addi=
and the =sw=, memory still held 25. The =addi= touched only the register, and
=$t0= never moved at all: a base is just a base.

The smallest complete data-transfer program is a swap: load both words
into registers, store them back crossed. Lecture 3's swap procedure is
exactly these four transfers wrapped in a call — the call machinery
that would wrap them arrives in Procedures and the Stack, later in the
series.

#+NAME: swap
#+BEGIN_SRC mips
# swap.asm — exchange the two words of pair in .data
        .data
pair:   .word 13, 29            # pair[0] = 13, pair[1] = 29
        .text
main:   la      $t0, pair       # $t0 = &pair[0] — the base address
        lw      $t1, 0($t0)     # $t1 = pair[0]: rt is the destination
        lw      $t2, 4($t0)     # $t2 = pair[1]: +4 bytes = one word up
        sw      $t2, 0($t0)     # pair[0] = $t2: rt is the source now
        sw      $t1, 4($t0)     # pair[1] = $t1
        lw      $a0, 0($t0)     # read pair[0] back from memory
        li      $v0, 1          # print it
        syscall
        li      $a0, 32         # ' ' between the two values
        li      $v0, 11
        syscall
        lw      $a0, 4($t0)     # read pair[1] back
        li      $v0, 1
        syscall
        li      $v0, 10         # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:29 13

Run it, then read the panels. The =Output= panel prints =29 13= —
=pair[0]= and =pair[1]= re-read from memory after the swap, which is
the proof the two =sw= instructions actually wrote. For the state
story, step instead of running: each =lw= flags the register it just
wrote in the =Registers= panel, and each =sw= flags nothing — its
effect lives in the =.data= panel, where the two 4-byte groups trade
places. The =Program= panel shows each instruction's encoded bytes:
=lw $t2, 4($t0)= appears as =8d 0a 00 04=, the offset =4= visible in
the last byte. The field-by-field decode is Machine Code: R, I, J, two
pages ahead.

Exam angle: the two classic marks here are the load-modify-store trace
above (register changes first, memory only at the =sw=) and the rt
role flip between =lw= and =sw=.

* Byte addressing: the ×4 rule

Mental model: addresses number bytes, not words and not array
elements. A word is 4 bytes, so consecutive words live 4 addresses
apart. If =a= starts at =0x10010000=, then =a[0]= is the word at
=0x10010000=, =a[1]= at =0x10010004=, =a[2]= at =0x10010008=. Think in
elements if you like; the machine counts in bytes.

The formal rule: element =i= of a word array based at =b= lives at
=b + 4 × i=. It has two working forms. Constant index: fold the
multiplication into the offset — =A[2]= sits at offset =8=, =A[6]= at
=24=, =A[8]= at =32=, so =lw $t0, 32($s0)= loads =A[8]= with no
scaling instruction at all. Variable index: the index reaches a
register only at run time, so scale it there — =sll $t2, $t0, 2=
multiplies by 4 in one shift, then =add= folds in the base.

Scale of the address space: 32 address bits number =2^32= bytes, a
word is 4 of them, so the space holds =2^30= words. Word addresses are
exactly the multiples of 4 — a T2 multiple-choice fact, and the seed
of the alignment trap two sections down.

#+NAME: array-sum
#+BEGIN_SRC mips
# array-sum.asm — sum a[0..3] with a scaled index
        .data
a:      .word 5, 10, 15, 20     # a[i] lives at a + 4*i bytes
        .text
main:   la      $s0, a          # $s0 = base address of a
        add     $s1, $zero, $zero # sum = 0
        addi    $t0, $zero, 0   # i = 0
        addi    $t1, $zero, 4   # n = 4: one past the last index
loop:   beq     $t0, $t1, done  # while (i != n)
        sll     $t2, $t0, 2     # $t2 = 4*i — the ×4 rule in one shift
        add     $t2, $s0, $t2   # $t2 = &a[i] = a + 4*i
        lw      $t3, 0($t2)     # $t3 = a[i] — the loop's only data access
        add     $s1, $s1, $t3   # sum += a[i]
        addi    $t0, $t0, 1     # i++
        j       loop            # back to the test
done:   move    $a0, $s1        # print the sum
        li      $v0, 1
        syscall
        li      $v0, 10         # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:50

Run it: the =Output= panel prints =50=. The layout it walked:

| address       | element | value |
|---------------+---------+-------|
| 0x10010000  | a[0]  |     5 |
| 0x10010004  | a[1]  |    10 |
| 0x10010008  | a[2]  |    15 |
| 0x1001000c  | a[3]  |    20 |

The addressing story is in the =Registers= panel. Click the gutter on
line 12 (the =lw=) to set a breakpoint, then ▶ Run: the machine pauses
just before it. Press Run again each lap — every pause finds =$t2=
four bytes further on: =0x10010000=, =0x10010004=, =0x10010008=,
=0x1001000c=, never once skipping or doubling. Across the laps =$t3=
takes =5=, =10=, =15=, =20= while =$s1= accumulates =5=, =15=, =30=,
=50=. The loop idioms themselves get their full treatment in Branches,
Loops, and C Translation, one page ahead.

The other indexing idiom drops the index and walks a pointer: bump the
address register itself by 4 each pass. HW1 Q5's loop is written this
way. Same addresses, same four loads — choose whichever fits the
question's register budget.

#+BEGIN_SRC text
# pointer walk — the same sum, the base register doing the walking
        addi    $t2, $s0, 0       # p = &a[0]
        addi    $t3, $zero, 4     # 4 elements to go
loop:   lw      $t4, 0($t2)       # *p — always offset 0 now
        add     $s1, $s1, $t4     # sum += *p
        addi    $t2, $t2, 4       # p += 4 bytes = one element
        addi    $t3, $t3, -1      # one element fewer
        bne     $t3, $zero, loop
#+END_SRC

Exam angle: T2 Q5 — base address =0x0000 1000=, each element 4 bytes,
"valid address for the 3rd element (index 2)" — answer =0x0000 1008=.
The distractors scale by 2 instead of 4, or read "3rd element" as
index 3. The same arithmetic sizes the address space: =2^32= bytes
over 4 gives =2^30= words.

* Laying out data: directives and the hexdump panel

Mental model: the =.data= segment is a byte stream you fill left to
right. An invisible cursor marks the next free byte; every directive
emits bytes and advances the cursor; a label names wherever the cursor
currently is. No types, no structure — bytes and a position.

- =.word v1, v2, …= — four bytes per value, written little-endian;
  rounds the cursor up to a multiple of 4 first
- =.byte v1, v2, …= — one byte per value, no alignment at all
- =.ascii "s"= or =.asciiz "s"= — the string's bytes; =.asciiz= appends
  the NUL (=0=) terminator that syscall 4 stops at
- =.space n= — =n= zero bytes of scratch, no alignment
- =.align n= — rounds the cursor up to the next multiple of =2^n=
There is also =.half= — two bytes, aligning to a multiple of 2 — rare
in this course. One block using all five directives of the list above:

#+NAME: data-directives
#+BEGIN_SRC mips
# data-directives.asm — five directives, twenty-four bytes of .data
        .data
val:    .word   0x2A            # 4 bytes: 2a 00 00 00
msg:    .asciiz "Hi!\nBye"      # 8 bytes: H i ! \n B y e NUL
        .byte   1, 2            # 2 raw bytes — no alignment padding
        .align  2               # round the cursor up to a multiple of 4
buf:    .space  8               # 8 zeroed bytes, now word-aligned
        .text
main:   la      $a0, msg        # syscall 4 prints up to the NUL
        li      $v0, 4
        syscall
        li      $v0, 10         # nothing to compute: this block IS its data
        syscall
#+END_SRC

#+RESULTS:
:Hi!
:Bye

Run it, then read the =.data= panel — the first 256 bytes of the data
segment, live. This block lays out 24 of them:

#+BEGIN_SRC text
0x10010000  2a 00 00 00 48 69 21 0a 42 79 65 00 01 02 00 00  |*...Hi!.Bye.....|
0x10010010  00 00 00 00 00 00 00 00                            |........|
#+END_SRC

Walk it against the directives. =val= is =2a 00 00 00=: the value
=0x2A= with its smallest byte first — hold that thought for the
endianness section. =msg= is =48 69 21 0a 42 79 65 00= — =H=, =i=, =!=,
newline, =B=, =y=, =e=, and the NUL that =.asciiz= promised; the
two-line =Hi!= / =Bye= in the Output panel is syscall 4 stopping at
that NUL. Then =01 02= from =.byte=, then =00 00=: two padding bytes
that =.align 2= inserted to round the cursor from 14 up to 16. =buf='s
eight zeros finish the layout. The ASCII column on the right renders
printable bytes and dots for the rest — =*...Hi!.Bye.....= — a quick
sanity check that strings are where you think they are.

Two alignment behaviors are worth separating. =.word= protects
itself: it auto-aligns to 4 before emitting, so a =.word= after an
odd-length string never lands crooked. =.space= and =.byte= do not
align, which is why the =.align 2= above is load-bearing: without it
=buf= would start at offset 14, and a later =lw= from =buf= would
trap. =.align= exists precisely to control labels and byte-level data
that the auto-aligning directives would leave at odd addresses.

The hexdump is not a static listing — it is the machine's memory, and
=sw= rewrites it while you watch. Go back to the =swap= block. Its
=.data= panel starts as =0d 00 00 00 1d 00 00 00= — that is =13= and
=29=, smallest byte first. Click the gutter on line 8, the first =sw=,
to set a breakpoint, then ▶ Run: paused before the store, the bytes
are unchanged. Step once: the first four bytes flip to =1d 00 00 00=.
Step again: the second word flips. Two =sw= instructions, eight bytes
rewritten, one panel — the memory picture T2 asks you to draw on
paper, animating itself.

* Alignment: why an off-by-one load traps

Mental model: memory serves whole words through fixed doors, one door
every 4 bytes, at addresses divisible by 4. =lw= and =sw= must name a
door. An address like =w+1= is in the middle of the wall — no 4-byte
word starts there.

The formal rule: the effective address of =lw= and =sw= must be a
multiple of 4. =lw $t0, 3($s3)= is illegal — the word it asks for would
straddle two aligned words, and serving it would take two accesses and
a byte shuffle. T2 draws exactly this: a row of aligned words, then a
"Misaligned" word spanning the boundary. Halfword accesses (=lhu= and
=sh=, on the reference card but outside the HW1 set) need a multiple
of 2; byte accesses (=lb= and =sb= here; the card's load entry is
=lbu=) go anywhere — that exemption is what the endianness probe
below exploits.

#+NAME: misaligned
#+BEGIN_SRC mips
# misaligned.asm — lw one byte past a word boundary (# fault-demo)
        .data
w:      .word 0x11223344        # w = 0x10010000, a multiple of 4
        .text
main:   la      $t0, w          # $t0 = &w
        lw      $t1, 0($t0)     # 0x10010000 % 4 == 0: aligned, runs
        move    $a0, $t1        # print what the aligned load fetched
        li      $v0, 1
        syscall
        lw      $t2, 1($t0)     # 0x10010001 % 4 == 1: the machine stops
        li      $v0, 10         # reached only after you fix line 10
        syscall
#+END_SRC

#+RESULTS:
:287454020

Run it. The =Output= panel shows =287454020= — that is =0x11223344=
in decimal, fetched by the aligned =lw= on line 6: the word really is
there. Then the machine stops, and the status span in the button bar
above the editor reads =error · line 10: lw $t2, 1($t0): unaligned
word access at 0x10010001 (lw/sw need 4-byte alignment)=. The error box
below the editor is for assembly-time errors only; this one ran. The
=Program= panel's
current-line marker sits on the trapping =lw= — the machine halted
before executing it, and =pc= never moved past. The fault is at run
time, on the computed address; the syntax was perfectly legal.

Fix it in the editor: change the offset =1= to =0= and Run again — the
load succeeds and the exit pair runs. The assembler also accepts the
label-arithmetic spelling =lw $t2, w+1=; it builds the same crooked
address through =$at= and faults the same way, at the same address —
the message names whichever source spelling produced it.

Exam angle: alignment is a standing item on the trap list — any =lw=
or =sw= whose computed effective address is not a multiple of 4 is
illegal, however legal its registers look. Expect it as a
multiple-choice distractor and as one line of a validity critique.

* Endianness: which byte lands first

Mental model: a 32-bit word is four bytes, and memory hands out four
single-byte slots in a fixed order — lowest address first. When
=0x11223344= moves in, something must decide which of its bytes takes
the first slot. That decision is the machine's endianness, and it is
the last byte-level fact you need.

Little-endian: the least significant byte takes the lowest address.
Big-endian: the most significant byte does. The course stance (Lecture
3, p.39): MIPS as specified is big-endian, x86 little-endian — and
this kernel, like SPIM on x86 hosts, runs little-endian. T2 presents
both orders side by side, and the exam expects you to produce either on
demand.

First, the constant. =0x11223344= fits no immediate field, so build
it the way Arithmetic and Logic taught: =lui $t0, 0x1122= sets the top
half, =ori $t0, $t0, 0x3344= ORs in the bottom half — zero-extended,
so the top survives. Then store it, and read the four bytes back one
at a time.

#+NAME: endian-probe
#+BEGIN_SRC mips
# endian-probe.asm — store one word, read its four bytes back
        .data
w:      .word 0                 # scratch word; its label is its address
        .text
main:   lui     $t0, 0x1122     # $t0 = 0x11220000 — upper half first
        ori     $t0, $t0, 0x3344 # $t0 = 0x11223344 — ori zero-extends
        la      $t1, w          # $t1 = &w
        sw      $t0, 0($t1)     # all four bytes change at once
        li      $t2, 4          # four bytes to visit
loop:   lb      $a0, 0($t1)     # the one byte at address $t1
        li      $v0, 1          # print it in decimal
        syscall
        addi    $t2, $t2, -1    # one byte fewer to go
        beq     $t2, $zero, out # after the last byte: leave the loop
        li      $a0, 10         # '\n' between two values
        li      $v0, 11
        syscall
        addi    $t1, $t1, 1     # next address: ONE byte up, not four
        j       loop
out:    li      $v0, 10         # syscall 10: exit
        syscall
#+END_SRC

#+RESULTS:
:68
:51
:34
:17

The =sw= writes the whole word at =w=; the loop reads it back with
=lb=, bumping the address by one each pass — note the contrast with
the array loop, which bumped by four. The =Output= panel prints four
lines: =68=, =51=, =34=, =17= — decimal for the bytes at =w+0= through
=w+3=, which in hex are =0x44=, =0x33=, =0x22=, =0x11=. The =.data=
panel agrees without a single =lb=: after the run its first four bytes
read =44 33 22 11= — the ASCII column even spells =D3".=. The least
significant byte sits at the lowest address: little-endian, confirmed
twice.

| address | little-endian (this kernel, SPIM on x86) | big-endian (the other column) |
|---------+------------------------------------------+-------------------------------|
| w+0   | 44                                     | 11                          |
| w+1   | 33                                     | 22                          |
| w+2   | 22                                     | 33                          |
| w+3   | 11                                     | 44                          |

The exam form (T2 Q7): for the 32-bit number =0x12345678=, how is it
stored on a big-endian system, and on a little-endian one? Big-endian:
=12 34 56 78=. Little-endian: =78 56 34 12=. The word's address is
the same either way, and an aligned =lw= or =sw= can never tell the
difference — the same 32 bits go in and come out. Endianness is
visible only to byte-level views: =lb=, the hexdump, and paper byte
diagrams.

Two footnotes on =lb=. It is not on the F26 reference card — the
card's byte-load entry is the zero-extending =lbu= — and it is outside
the HW1-taught set; this page borrows it as a measuring instrument,
the only way to see one byte at a time. And it
sign-extends: every byte of =0x11223344= has its top bit clear, so the
four prints came out positive, but a byte at or above =0x80= would
print negative — =lb= of =0x88= gives −120. =lbu= is the zero-extending
twin, and =sb= stores a single byte.

* What counts as a memory access

Mental model: registers and memory are two rooms with one door between
them. A register has no address and never touches memory; a memory
word never touches arithmetic. Only loads and stores cross — so
counting memory accesses means counting executed loads and stores, and
ignoring everything else.

The counting rule, straight from HW1 Q8: each executed =lw= is one
data-memory read, each executed =sw= is one write. Everything else —
=lui=, =ori=, =add=, =sub=, =sll=, =slt=, =beq=, =j=, and all address
formation — touches registers only. Building an address in a register
is register work, however memory-flavored it looks.

#+BEGIN_SRC text
# HW1 Q8 — how many times is memory accessed?
lui     $t1, 0xBBEE         # builds 0xBBEE0000 in a register — no access
ori     $t1, $t1, 0xABCD    # $t1 = 0xBBEEABCD — still only registers
lw      $s1, 1024($t1)      # reads Mem[0xBBEEAFCD] — access 1
sub     $s1, $t1, $s1       # register subtraction — no access
sll     $s2, $s4, 3         # register shift — no access
lw      $t2, -4($t1)        # reads Mem[0xBBEEABC9] — access 2
sw      $t6, -128($s2)      # writes Mem[$s2 - 128] — access 3
#+END_SRC

Walk it the way the marker wants, data half first. The =lui= and =ori=
pair builds =0xBBEEABCD= — pure register work, as are the =sub= and
the =sll=; that is why each contributes 0 data accesses. The two =lw=
read =Mem[0xBBEEAFCD]= and =Mem[0xBBEEABC9]=: 1024 is =0x400= added,
−4 subtracted, both sign-extended offsets doing address arithmetic.
The =sw= writes one word. Data accesses: 3. But the official solution
(F26 HW1 Solutions, p.25) answers 10 — those 3 data accesses plus 7
instruction fetches, one per executed instruction of the snippet. HW1's
hint — "What is stored in memory? Memory and registers are not the
same." — is steering you to count both halves: the program itself sits
in memory, and every step fetches its instruction word before any
=lw= or =sw= touches data.

Audit every block on this page the same way. The array sum's status
line after a Run reads finished · exit(0) · 39 steps — and of those 39
executed instructions exactly 4 touched data memory, the =lw= running
once per element. The swap block: 17 steps, 6 accesses — four =lw=,
two =sw=. The endianness probe: 43 steps, 5 accesses — one =sw=, four
=lb= (byte accesses count too; they are just outside the HW1 set).
Yes, every one of those steps also fetched an instruction word from
text memory — the stored-program fact from The Machine Model, and the
other half of the official count. On HW1 Q8 the expected answer names
both halves — instruction fetches plus data accesses — with the
reasoning shown.

* Exam drills this page prepares you for

- A7, memory-access counting (HW1 Q8): the data half is executed =lw=
  and =sw= only — address formation and register arithmetic are free —
  and the official answer adds the instruction fetches on top (Q8: 7
  fetches + 3 data = 10); show the line-by-line reason, not just the
  number.
- A9, address arithmetic: the ×4 rule (=A[2]= at offset =8=, T2 Q5's
  =0x0000 1008=), =2^30= words in a 32-bit address space, and the
  misaligned-=lw= illegality.
- A10, endianness and storage layout: both byte orders of =0x12345678=,
  read off a byte diagram or a hexdump.
- The array half of A1, C→MIPS translation: scale a variable index
  with =sll …, 2= or fold a constant index into the byte offset.
- The array half of A6, full-program traces: predict element values,
  =sw= execution counts, and the memory picture after the loop — then
  check yourself against the =.data= panel.
