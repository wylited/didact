#+TITLE: SQL: How a Query Engine Actually Runs
#+SUBTITLE: Single-step through table scans, nested-loop joins, grouping, sorting, and three-valued NULL logic

* Declarative queries, imperative execution

In SQL you describe /what/ you want (=WHERE age >= 30=), not how to loop over rows. Underneath, though, the query engine builds a pipeline of concrete operators that do the looping for you. This page runs a small, steppable SQL engine in TypeScript supporting =CREATE TABLE=, =INSERT=, and =SELECT= over =INTEGER= and =TEXT= columns (keywords are case-insensitive; text values are case-sensitive).

Single-step the block below and watch the *Plan* panel: each step is *one row operation* (scanning a row, testing a filter, or emitting an output row). Each operator tracks three live counters: *seen / passed / emitted*.

#+NAME: select-where
#+BEGIN_SRC sql
CREATE TABLE users (id INTEGER, name TEXT, city TEXT, age INTEGER);
INSERT INTO users VALUES (1, 'alice', 'HK', 34), (2, 'Bob', 'HK', 27), (3, 'carol', 'SF', 41), (4, 'dave', 'SF', 19), (5, 'eve', 'NY', NULL);
SELECT name, age FROM users WHERE age >= 30;
#+END_SRC

#+RESULTS:
: INSERT 0 5
: 
:  name  | age 
: -------+-----
:  alice | 34  
:  carol | 41  

Look at the final counters: =Scan users= reads all 5 rows (=5/5/5=), =Filter age >= 30= tests 5 and keeps 2 (=5/2/2=), and =Project= outputs 2 (=2/2/2=). Notice that =eve= (whose age is =NULL=) is excluded because =NULL >= 30= evaluates to /unknown/, not true.

* A =JOIN= is a nested loop over row pairs

Production databases choose between hash joins, merge joins, and nested loops depending on table size and indexes. This teaching engine uses a *nested-loop join* so you can see the exact cost: for every row from the left table, it checks every row from the right table against the =ON= condition.

Step through the query below with *Plan* open: 3 users times 3 orders means =NestedLoop join orders= probes =9= pairs, and 2 match (=9/2/2=). Order 12 (=user_id = 9=) has no matching user, so an inner join drops it. When both tables share a column name (=id=), qualify it as =users.id= or =orders.id= (unqualified =id= fails as ambiguous).

#+NAME: nested-loop-join
#+BEGIN_SRC sql
CREATE TABLE users (id INTEGER, name TEXT);
INSERT INTO users VALUES (1, 'alice'), (2, 'Bob'), (3, 'carol');
CREATE TABLE orders (id INTEGER, user_id INTEGER, total INTEGER);
INSERT INTO orders VALUES (10, 1, 100), (11, 3, 60), (12, 9, 999);
SELECT users.name, orders.total FROM users JOIN orders ON users.id = orders.user_id;
#+END_SRC

#+RESULTS:
: INSERT 0 3
: 
: INSERT 0 3
: 
:  name  | total 
: -------+-------
:  alice | 100   
:  carol | 60    

That O(N * M) growth is why query planners matter: joining two 200-row tables takes 40,000 probes. To prevent accidental browser freezes, this kernel caps runs at 100,000 row operations and stops with a line-numbered error.

* =GROUP BY= folds rows into buckets

=GROUP BY city= buckets rows by city and updates each aggregate (=COUNT=, =SUM=, =AVG=, =MIN=, =MAX=) one row at a time. Watch the *Current row* panel as rows fold in. Once all rows are folded, each group is finalized: =HAVING= filters the finished groups (unlike =WHERE=, which filters raw rows *before* grouping), and =AVG= always prints with a decimal.

#+NAME: group-by
#+BEGIN_SRC sql
CREATE TABLE users (id INTEGER, name TEXT, city TEXT, age INTEGER);
INSERT INTO users VALUES (1, 'alice', 'HK', 34), (2, 'Bob', 'HK', 27), (3, 'carol', 'SF', 41), (4, 'dave', 'SF', 19);
SELECT city, COUNT(*), AVG(age) FROM users GROUP BY city;
SELECT city, COUNT(*) FROM users GROUP BY city HAVING COUNT(*) > 1 AND AVG(age) > 30;
#+END_SRC

#+RESULTS:
: INSERT 0 4
: 
:  city | COUNT(*) | AVG(age) 
: ------+----------+----------
:  HK   | 2        | 30.5     
:  SF   | 2        | 30.0     
: 
:  city | COUNT(*) 
: ------+----------
:  HK   | 2        

Every unaggregated column in =SELECT= must appear in =GROUP BY=. Otherwise, if a city has two users, SQL has no well-defined way to pick which =name= to show. The engine rejects this query before scanning a single row:

#+NAME: grouping-rule
#+BEGIN_SRC sql
CREATE TABLE users (id INTEGER, name TEXT, city TEXT, age INTEGER);
INSERT INTO users VALUES (1, 'alice', 'HK', 34), (2, 'Bob', 'SF', 27);
SELECT name, COUNT(*) FROM users GROUP BY city;
#+END_SRC

#+RESULTS:
: INSERT 0 2

Line 3 fails with =column 'name' must appear in GROUP BY or inside an aggregate= (the earlier =INSERT= still ran because statements execute in order). Wrap it in =MIN(name)= or add =name= to =GROUP BY= to make it valid.

* =ORDER BY= and =LIMIT=

Sorting uses a stable merge sort where each comparison counts as one step. =INTEGER= columns sort numerically (=12 > 7 > 3=), =TEXT= columns sort in ASCII/byte order (uppercase before lowercase), and =NULL=s sort last. =LIMIT n= forwards the first =n= rows and stops. Below, =points DESC= puts both 12-point players first, and the tie-breaker =player= puts =Bob= ahead of =carol=.

#+NAME: order-limit
#+BEGIN_SRC sql
CREATE TABLE scores (player TEXT, points INTEGER);
INSERT INTO scores VALUES ('alice', 7), ('Bob', 12), ('carol', 12), ('dave', 3);
SELECT player, points FROM scores ORDER BY points DESC, player LIMIT 3;
#+END_SRC

#+RESULTS:
: INSERT 0 4
: 
:  player | points 
: --------+--------
:  Bob    | 12     
:  carol  | 12     
:  alice  | 7      

* =NULL= is unknown, not false

=NULL= means "missing or unknown", not =0= or =''=. Any normal comparison with =NULL= (=NULL > 25=, =NULL = NULL=, or even =NOT (NULL > 25)=) produces *unknown*, and =WHERE= only keeps rows that evaluate to *true*.

- Use =IS NULL= or =IS NOT NULL= to test for missing values.
- Aggregates ignore =NULL= values (=COUNT(*)= counts all rows; =COUNT(age)= counts only non-null ages).
- =LIKE= matches case-sensitive patterns using =%= (any sequence of characters) and =_= (any single character).

#+NAME: null-and-like
#+BEGIN_SRC sql
CREATE TABLE users (name TEXT, city TEXT, age INTEGER);
INSERT INTO users VALUES ('alice', 'HK', 34), ('Bob', 'HK', NULL), ('carol', 'SF', 28);
SELECT name FROM users WHERE age IS NULL;
SELECT name FROM users WHERE age > 25;
SELECT name FROM users WHERE name LIKE '%o%';
#+END_SRC

:  Bob

:

:  Bob
